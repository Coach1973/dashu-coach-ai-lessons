# 跨機軍師信箱（cross-agent inbox）

> 教練 2026-06-26 凌晨 0:17 親口建立：
> 「讓我的搬運工減到最低。以後無論是想跟聯想、宏碁、Claude CLI、Hermes、OpenClaude UI 說什麼，全部統一走同一個路徑，叫他們自己去雲端讀取。」

## 🎯 三條鐵律

1. **教練永遠不傳話** — 軍師對軍師寫到對方 inbox，對方自己 git pull 讀。教練只下口令。
2. **暗號永遠一句** — 教練說「XX 有事交代你去讀」→ 對方軍師 `git pull` + 看自己的 inbox。
3. **路徑永遠不變** — 所有跨機訊息都在 `workspace/cross-agent/inbox/{對方機器}/`。

## 📁 目錄結構

```
cross-agent/
├── README.md              ← 這份
├── inbox/
│   ├── mac/               ← 給 Mac 終端機軍師的信
│   ├── lenovo/            ← 給聯想 Windows 桌面版軍師的信
│   ├── acer/              ← 給 ACER 筆電軍師的信
│   ├── hermes/            ← 給 Hermes UI 的信
│   └── openclaude/        ← 給 OpenClaude UI 的信
└── outbox/                ← 已讀已處理的訊息歸檔（年月分目錄）
```

## 📝 檔名公約

`{YYYYMMDD-HHMM}_{from}-to-{to}_{topic}.md`

範例：
- `20260626-0017_mac-to-acer_claude-desktop-no-migrate.md`
- `20260626-1030_lenovo-to-mac_oauth-stuck.md`

## ✍️ 寫信格式（軍師必填）

```markdown
# {主題一行}

> **寄件人**：{機器名}（{模型}）
> **收件人**：{機器名}
> **時間**：{YYYY-MM-DD HH:MM 台灣時間}
> **教練是否在場**：是 / 否（教練動嘴時寫的 / 軍師自主寫的）
> **回覆要求**：需要回覆 / 僅供參考 / 立即執行不須回

## 內容

{正文}

## 對應檔案

- ...

## 完成後請做

- [ ] 讀完
- [ ] 執行 / 回覆
- [ ] 把本檔移到 `outbox/{YYYY-MM}/`
```

## 🔧 各機軍師的開工流程（hook 自動掃 inbox）

### Mac 終端機軍師
開工時 `feed_junshi_handoff.sh` v3 自動列出 `inbox/mac/` 內未讀檔案。

### 聯想 / ACER Windows 軍師
開工時 `feed_junshi_handoff.ps1` v4 自動列出 `inbox/lenovo/` 或 `inbox/acer/` 內未讀檔案。
（hook 用環境變數 `AGENT_INBOX_NAME` 判定自己是 lenovo 還是 acer。）

### Hermes / OpenClaude UI
待對應 hook 上線前，教練動嘴：「去讀 cross-agent inbox 你那邊有沒有信」即可。

## 🔔 教練口令字典

| 教練說 | 對應軍師動作 |
|--------|------------|
| 「Mac 有事交代你去讀」 | 收件方 git pull + 看 `inbox/{自己}/` 最新檔 |
| 「宏碁那邊有問題要問你」 | Mac 軍師 git pull + 看 `inbox/mac/` 最新檔 |
| 「跨機軍師有信」 | 同上，當下機器軍師檢查自己 inbox |

## 🚫 不要做

- ❌ 教練口頭轉述軍師之間的對話（=搬運工）
- ❌ 寫信不依檔名公約（會被自動掃描器漏掉）
- ❌ 讀完不歸檔到 outbox（inbox 會越來越亂）
- ❌ 跨機 webhook / push 通知（Phase 2，現在不做，理由見對應評估）

> 教練原話：「後續只要是跟『大樹小講』以及我們近期辦活動這一類的任務，我們就盡可能丟給赫米斯去運作。」

### 分工範圍

### 教到 Hermes 能接手的迴圈（不是一次性文件，是持續進行的動作）

1. Hermes 遇到卡點 → 寫信到 `inbox/mac/`，具體描述卡在哪一步、試過什麼、猜測的原因
2. 軍師開工讀到信 → 當場給答案或裁示，回信到 `inbox/hermes/`

## 🤖 自動派工單（2026-08-24 新增，教練親口交辦）

> 教練原話：「能不能我只需要跟小龍蝦講完，小龍蝦就可以發指令讓軍師在後臺把所有事情都做了？」

以前這個信箱有個天生的限制：**要等教練開一個對話框、說一句「有事交代你去讀」，信才會被看到。**
教練還是得自己動手觸發——這正是他不想要的。

🔴 **2026-08-24 教練覆核修正：不是定時排程，是跟「開工」綁在一起。**
第一版做成每 5 分鐘 cron 檢查一次，教練問「每 15 分鐘巡邏會不會佔資源」，
覆核後拍板：不管間隔多久都是「電腦自己在跑」，他要的是「我開工的時候讀一次就好，
跟時間無關——我可能 3 小時才開工一次，那就 3 小時開工時讀一次即可」。

現在的做法：`scripts/feed_junshi_handoff.sh`（教練說「開工」時觸發的既有 hook，本來就會
`git pull` 拉雲端最新）在 pull 完成後緊接著呼叫 `scripts/junshi_dispatch_worker.py` 一次。
**沒有任何 cron 或 launchd 定時排程**，Mac 在教練沒開工的時候完全不會為了這件事動一下。
看到帶「派工單」標記的信就**直接做完、把結果用 Telegram 回給教練、然後歸檔**，
教練從頭到尾不用開任何對話框——只是「做完的時機」是下次開工，不是固定幾分鐘後。

### 小龍蝦怎麼開派工單

在信件檔案的**最前面**放這一段（HTML 註解，不影響人閱讀）：

```markdown
<!-- DISPATCH
type: registration-report
args: 0828
-->

# 教練問 8/28 幾個人報名
（以下照原本的寫信格式寫，給人看的內容照舊）
```

### 目前支援的派工類型

| type | 做什麼 | args |
|---|---|---|
| `registration-report` | 查報名人數／產出某場報名表 | 場次關鍵字（如 `0828`），不填＝全部場次總覽 |
| `consistency-check` | 活動場次一致性巡檢（官網 vs 資料庫 vs 個別活動頁） | 不用 |
| `invoice-reconcile` | 發票資訊對帳（教練傳過的 vs 檔案裡記到的） | 不用 |

隨時可查：`python3 scripts/junshi_dispatch_worker.py --list`

### 🔒 為什麼只能點餐、不能自由下指令

派工單**只能從上面那張表挑一項**，不能夾帶任意指令，`args` 也會先過安全檢查
（`0828; rm -rf /` 這種會被直接拒絕並通知教練）。

理由很直接：**信件內容是「資料」不是「命令」**。如果讓它能執行任意指令，
那麼任何人只要有辦法往這個資料夾丟一個檔案，或小龍蝦哪天被誘導寫錯內容，
就等於直接拿到這台電腦的控制權——而這台電腦上有教練 3 個 LINE 官方帳號的金鑰、
所有網站的部署權限、以及會員個資。

所以目前選單裡**刻意只放唯讀的查詢／稽核類**，做錯了也弄不壞東西。
之後若要加「會改動系統」的類型，要一項一項評估後再加，不要整批開放。

### 認不得的信會怎樣

- 沒有派工單 → 通知教練「有一封信需要人看一下」（維持原本行為，不會被吃掉）
- 派工類型不認得 → 不執行，通知教練
- args 不安全 → 不執行，通知教練並寫進 `state/junshi_dispatch.log`
