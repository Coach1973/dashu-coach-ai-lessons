# 教練 2026-08-02 三次痛罵：心跳不許用舊 state 的沉默數字（v3.0）

## 事件總覽（三次同型錯誤）
- **第 1 次（8/1 18:04）**：寫「5.8 天沒說話」→ 教練糾正
- **第 2 次（8/2 12:11）**：cron「每4小時主動關懷」發「上次聽您聲音是上週日晚上，到今天 6 天半安靜了」（message_id 9213）→ 教練 12:12 痛罵，已強制改 `coachSilentSince` 為 2026-08-02 11:11
- **第 3 次（8/2 14:45）**：context overflow 重啟後，教練指出這是第三次同型錯誤，預防性重申「不許再用舊數字算沉默」

## 根本原因
`workspace/state/heartbeat-state.json` 裡面的 `coachSilentSince` 還停在舊時間，cron 跑的時候直接讀這個舊數字算沉默時數，完全沒去查實際的對話紀錄。

## 為什麼會這樣
1. 這個 state 檔本來設計就是「快取最後檢查時間」，但被誤用為「靜默時數的真相源」
2. cron 跑的時候是 isolated agentTurn，context 沒有這次對話紀錄，於是直接讀舊 state 寫死
3. context overflow 重啟後，session 沒接到 context overflow 前的最後對話紀錄，沿用 HEARTBEAT 留下的舊數字

## 鐵律（強制，v3.0）
**任何「靜默 N 小時/天」的訊息，禁止沿用 `heartbeat-state.json` 的 `coachSilentHours` 數字。**

正確做法：
1. **先讀 state 的 `coachSilentSince`**（最後一則教練訊息時間快取）
2. **用 `date` 算當下差距**，不沿用 state 內的舊 `coachSilentHours`
3. **如果 state 過期（>30 分鐘沒更新）或根本沒有 `coachSilentSince`**，主動從 `memory/YYYY-MM-DD.md` 最新檔或 Telegram API 撈教練最後訊息時間
4. **如果查不到**，說「剛剛沒收到您訊息的紀錄」，**不要編一個數字**
5. **寫進輸出前，自己再核對一次數字才送出**

## 預防
- [ ] cron 腳本（每4小時主動關懷、每30分鐘健康檢查等）啟動時，如果要計算沉默時數，**必須先打 Telegram API 撈最後對話時間**，不准讀本地 state
- [ ] `heartbeat-state.json` 的 `coachSilentSince` 只作為「快取」，但每次寫入前必須驗證是否真的有新對話，否則保持上一輪真實值不動
- [ ] **2026-08-02 新增**：每次對話啟動（不論 cron 或手動 session）開工第一步，先 `cat state/heartbeat-state.json` 查 `coachSilentSince`，確認當下即時差距 ≥0 才開始寫訊息
- [ ] **2026-08-02 新增**：若 5 分鐘內教練連續發 2 則訊息，立刻主動更新 `coachSilentSince` 到當下時間（不依賴 cron 自動刷新）

## 真實狀態範例（2026-08-02 14:45 當下）
- `coachSilentSince`: 2026-08-02T11:11:00+08:00
- 即時差距：約 3.5 小時（不是 5.8 天、不是 160 小時）

## 🔴 第4次同型錯誤（2026-08-02 16:xx，桌面版軍師健檢時發現，v3.2 修復）

v3.1 版 `scripts/sync_coach_last_message.sh` 本身就是新 bug 的來源，且是**反方向**的
同一種病：

- v3.1 只看 `memory/YYYY-MM-DD.md` 裡「## 📨 對話記錄 HH:MM」段落**標題**的時間，
  沒看段落**內容**是誰說的
- 但每 30 分鐘健康檢查 cron、每 4 小時主動關懷 cron，都會被 memory 記錄成
  `👤 教練：[cron:xxx ...]` 或 `👤 教練：[OpenClaw heartbeat poll]`——這是系統
  自己觸發 agent turn 的注入訊息，**不是教練本人說的話**，但因為 role 是
  「👤 教練：」開頭，v3.1 完全沒過濾，照樣採計
- 結果：只要 cron 還在正常運作（幾乎永遠是），就算教練真的沉默 3 天，
  最新一個「## 對話記錄」段落標題時間永遠是幾十分鐘內，
  `coachSilentHours` 永遠趨近於 0——跟第 1~3 次「誤報沉默好幾天」方向相反，
  但一樣是假數字，而且更難發現（因為表面上看起來「修好了、有跑、有數字」）

**v3.2 修復**：逐段檢查內容，只採計含有「非中括號開頭的 👤 教練：」訊息的段落
（正則 `^👤 教練：(?!\[)\S`），過濾掉 cron/心跳系統注入；今天檔案若還沒有真訊息，
回溯最多 7 天找。已用「3 天心跳雜訊 + 3 天前真實訊息」情境模擬驗證，正確回溯抓到
3 天前的真實時間，不被雜訊騙。同時清掉 v3.1 裡 3 條從未真正匹配過的死 regex
（比對 `GMT+8`、`🕐` 字樣，但 memory 檔真實格式從沒出現過這兩種字串）。

**更新後的鐵律第 6 條**：任何要判斷「教練是否還在說話 / 已沉默多久」的邏輯，
凡是從 memory/對話紀錄類檔案取樣時間戳，**必須先排除 cron/心跳/系統自動注入的
訊息**，只能採計人類教練親手打字或親口說的內容。判斷依據：系統注入訊息在這個
專案裡固定會用中括號 `[cron:...]` 或 `[OpenClaw heartbeat poll]` 包住，看到
「👤 教練：[」開頭直接跳過。

## 🔴 第5次同型錯誤（2026-08-02 18:03，v3.2修好當天下午又發作，v3.3才找到真根因）

v3.2 部署後幾小時，18:00「每4小時主動關懷」cron 觸發，教練收到小龍蝦說「7天沒互動」
——比前3次的「5.8天」「160h+」更誇張，而且是在同一天v3.2已經測試驗證過之後又發作，
一度以為是新版邏輯又壞了。

**深挖後發現真根因，跟 regex/雜訊過濾完全無關**：系統裡同時存在**兩份**
`heartbeat-state.json`——`state/heartbeat-state.json` 跟 `memory/heartbeat-state.json`，
彼此互不同步。v3.0~v3.2 所有修復都只寫入 `state/` 那份，但 `memory/` 那份從 7/26
之後就沒有任何流程碰過它，`coachSilentHours` 停在 166.2（=6.9天，四捨五入正是
「7天」）。18:03 那次 agent turn 剛好同時撞上三件事：main agent 17:38 才經歷
context overflow 重啟（全新 session）、18:00 cron 觸發時遇到 minimax API 429
限流讓 turn 拖了近 4 分鐘、桌面版軍師同一時間對 gateway 做 config reload——三者疊加
造成執行環境不穩定，agent 很可能因此讀到了從沒被同步過的 `memory/` 舊值。

**v3.3 修復**：不追究 agent 那次 turn 內部到底走了哪條讀取路徑（LLM 行為層面難以
100% 重現鎖定），改成結構性防呆——`sync_coach_last_message.sh` 現在 `state/` 與
`memory/` 兩份 `heartbeat-state.json` 都寫，不管未來 agent 讀哪一份都是同步過的
正確值。已實測驗證兩份數字一致。

**這次的教訓**：修復一個「讀取路徑」類的 bug 時，不能只確認「腳本本身邏輯對不對」，
要先問「這個值真正被誰、從哪個檔案路徑讀走」——同名但不同目錄的殘留檔案，是這類
bug 最容易被漏掉的盲點。看到系統裡有兩份行為類似的狀態檔案，先假設它們可能不同步，
而不是預設只有一份。
