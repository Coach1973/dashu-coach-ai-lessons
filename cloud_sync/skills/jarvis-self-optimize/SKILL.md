# 賈維斯智慧體的自我檢測系統

教練 2026-10-21 定：規則越少越好；越定越多不是智慧。要的是精準、高效率、不會犯錯的遊戲規則，只保留越用越好用的東西。聽到口令直接跑完整套，不問「要不要」。

## 三條總原則（每一步都用它判斷）

1. **一進一出**：這次體檢結束時，常駐規則總字數必須持平或下降。要新增一條，就同時刪掉或合併一條。
2. **能做成機制就不留條文**：必須每次都做到的事，放程式（擋下／自動修／預設值），不放「請記得」。條文只留程式管不到的判斷。
3. **證據決定去留**：一條規則留不留，看它最近有沒有命中、有沒有救到人；不看它當初多重要。危險指令類例外（本來就很少命中）。

## 執行路徑

### 第 0 步：改前備份
所有會改到的規則檔複製到 `workspace/state/backup_<日期>_jarvis/`，寫一行清單。守則 21 條原文（特助心法.md）一字不動。

### 第 1 步：機械體檢（零額度）
```bash
python3 ~/.openclaw/workspace/scripts/rules_health_audit.py
```
讀 `distill/rules_health_report.md`：過時路徑、重複段落、總字數趨勢、反射命中。
量字數一律用 `python3 -c "print(len(open(f,encoding='utf-8').read()))"`；`wc -m` 在這台 Mac 算的是位元組，中文會多算約 3 倍（2026-10-21 第一次執行就算錯）。

### 第 2 步：五問逐項查（每問都要有工具查到的證據）

| 問題 | 怎麼查 | 判斷 |
|---|---|---|
| ① 運行良好嗎？ | 各鎖的紀錄 `distill/rule_*_violations.log`、反射命中 `state/reflex_hits.log`、審查員帳本 `distill/rules_reviewer_ledger.jsonl`、教練糾正次數 `scripts/rules_reminder_count.py --weekly`、守門員日誌；hook 有沒有真的掛在 `~/.claude/settings.json`、腳本在不在 | 有掛、有命中、命中是對的＝良好。從沒觸發要先確認是「沒人犯」還是「根本沒接上」（案例 98） |
| ② 有沒有打架？ | 同一主題的規則並排比（例：執行細則 N3 第一段「先搜尋」對第二段「先問」） | 列出每一組衝突與建議留哪一邊 |
| ③ 有沒有重複？ | 第 1 步的重複段落＋語意重複：同一件事同時寫在記憶、反射、Stop 規則、CLAUDE.md 幾處 | 只留最強的那一處（程式＞擋下＞提醒＞記憶），其他刪掉或改成一行「見某處」 |
| ④ 佔容量沒效率？ | 每場常駐字數（全域＋專案 CLAUDE.md）、小龍蝦開機檔對照上限（`openclaw.json` 的 bootstrapMaxChars）、提醒最吵前 5 名、90 天沒命中的 | 超上限＝會被截掉（默默失效），列第一優先 |
| ⑤ 能更好嗎？ | 對照升降級：提醒擋不住同類錯→升擋下或改程式；擋下誤擋多→改設計；三份記憶講同一件→合一；外部做法（見下） | 每一條建議都要寫「改完少多少字／少犯哪一類錯」 |

### 第 3 步：外部經驗（三大信念二：先找證明有效的做法）
每次都花一輪搜尋：Claude Code 官方文件的 CLAUDE.md 與 hooks 更新、OpenClaw 最新版說明（docs.openclaw.ai/releases）、Hermes 更新。有新功能能取代我們自己寫的規則或腳本，就列入建議。已知且仍成立的結論：
- 研究一致顯示：同時給 AI 的指令越多，遵守率越低，排在中間的規則最容易被漏掉。
- CLAUDE.md 是指引不是強制；每次都必須做到的放 hook。
- 兩條規則打架時，AI 可能隨便選一邊。

### 第 4 步：處置分級（誰可以改）
- **AI 直接改並存檔**：死路徑、重複副本改成「見某檔」、壞掉沒接上的機制、超過平台上限的開機檔瘦身（內容搬去按需讀的檔，不刪資訊）。
- **出建議、教練拍板才改**：執行細則與 CLAUDE.md 的條文增刪、任何會改變行為的規則。
- **一字不動**：守則 21 條原文。

### 第 5 步：各平台各自做到最佳（不是全部照搬）

| 平台 | 限制 | 最佳做法 |
|---|---|---|
| Mac 軍師（Claude 桌面版／終端機） | 常駐檔每場都佔容量；有 hook、技能 | 常駐檔只留身份＋口令對照；強制的放 hook；流程放技能（用到才載入） |
| 小龍蝦 LINE／Telegram（OpenClaw，MiniMax） | 開機檔有字數上限，超過會被截；舊式 hook 的「注入」送不到模型（案例 98）；LINE 推播扣額度；改規則後舊對話仍用舊規則（案例 95） | 開機檔壓在上限 8 成內；要即時提醒用 before_prompt_build 外掛；改完刪舊對話再用真實群組實測；規則寫得更短更白話（模型較小） |
| 赫米斯（Mac 桌面版 Hermes.app） | 規則在 `~/.hermes/SOUL.md`，不在 git | 改前備份；改完 `hermes -z` 開新對話實測 |
| VPS 小龍蝦（外部朋友版，43.245.60.200） | 9 位外部用戶、記憶隔離；不該帶教練私人規則 | 只放通用守則；先讀 VPS 上的路徑大全再改；改完用一位測試用戶實測 |
| 雲端 Claude 對話 | 只讀倉庫裡的 CLAUDE.md，沒有 hook | 用規則包同步（`scripts/cloud/sync_rules_to_repos.py`），只放最精簡版 |

### 第 6 步：驗證
每個改動走該平台真實的使用路徑實測一次；跑 `scripts/test_stop_rules_master.sh`；再跑一次第 1 步，**總字數必須比改前少或持平**，寫進報告。

### 第 7 步：交付
做一頁 HTML 報告（Artifact）：五問各自的結論、改了什麼（附存檔編號）、刪了多少字、等教練拍板的建議（每項一句話＋好處）。跑 `scripts/deliver_open.sh <網址>` 跳出來；Artifact 會自動收進大樹作品集。回覆只放 3～5 行重點＋網址。最後 commit＋push 給存檔編號。

## 什麼時候跑
教練說口令時跑完整套。另外每週一 08:10 點名會算賈維斯成績單（`scripts/jarvis_scorecard.py`：教練糾正、新案例、同類重犯、規則總字數），任一項變差就自動在背景跑一次（`scripts/jarvis_scorecard_trigger.sh`，同一週最多一次，只做「AI 直接改」類，報告傳教練 Telegram）。收工時 `rules_health_audit.py` 已自動跑機械層；看到字數變多，收工回報順帶一句即可。
