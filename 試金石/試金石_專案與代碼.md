## 📍 案例 003：watchdog 假回報（說了等於做到是假的）

**嚴重程度：** 🟠 高

### 錯誤描述
log 顯示 osascript 因為 macOS 權限被拒，但腳本仍然寫「✅ 已送出繼續指令」成功訊息。

### 根因分析
腳本沒有檢查 exit code，失敗了還說成功——等於在撒謊。

### 正確做法
```bash
# 抓 exit code + stderr
osascript -e 'tell application "System Events" to...' 2>&1
exit_code=$?

if [ $exit_code -ne 0 ]; then
    echo "❌ osascript 權限被拒"
    # 錯誤訊息寫進 log
else
    echo "✅ 繼續指令已送出"
fi

# 去重：24 小時內同樣錯誤只寫一次
# 連續失敗 3 次以上 → 寫進 HEARTBEAT.md
```

1. 任何腳本的成功訊息 → 要檢查 exit code
2. 失敗寫 ❌，成功寫 ✅，不要都寫 ✅

## 📍 案例 004：增量蒸餾腳本不存在，但 cron 在跑（案例 C / #9）

## 📍 案例 W01-2026-06-25：Windows AppData 搬移 SOP（血淚版）

**嚴重程度：** 🔴🔴🔴 極高（4 小時損失）
**觸發情境：** 用戶說「幫我把 C 碟資料移到 D 碟」

### 背景

2026-06-25，軍師幫教練將 Claude 及 Comet 等 App 的 AppData 從 C 碟搬到 D 碟，
使用 Junction 方法。結果 Claude Desktop 完全無法啟動、Comet 捷徑失效。
歷時 4 小時才修復。

### 根因

Junction 只移動資料夾本體，以下四個 Windows 參考點**完全不會自動更新**：
- Windows 捷徑（.lnk）的 TargetPath
- Registry 的 InstallLocation / UninstallString
- USER 層環境變數
- 第三方工具（如 cc-switch）的干擾

### ✅ 正確 SOP（七步驟，缺一不可）

```powershell
# === 步驟 0：備份 ===
$appName = "Comet"  # 替換成目標 App 名
$srcPath = "$env:LOCALAPPDATA\Perplexity\Comet"  # 替換
$dstPath = "D:\Claude-Data\Perplexity\Comet"     # 替換
$ts = Get-Date -Format "yyyyMMdd-HHmmss"
Copy-Item $srcPath "$srcPath.bak.$ts" -Recurse -Force

# === 步驟 1：捷徑審計 ===
$sh = New-Object -ComObject WScript.Shell
Get-ChildItem "$env:USERPROFILE\Desktop", "$env:APPDATA\Microsoft\Windows\Start Menu" -Recurse -Filter "*.lnk" | ForEach-Object {
    $lnk = $sh.CreateShortcut($_.FullName)
    if ($lnk.TargetPath -like "*$appName*") {
        Write-Host "捷徑: $($_.FullName) -> $($lnk.TargetPath)"
    }
}

# === 步驟 2：Registry 審計 ===
Get-ChildItem "HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall" |
    Where-Object { (Get-ItemProperty $_.PSPath).DisplayName -like "*$appName*" } |
    ForEach-Object {
        $p = Get-ItemProperty $_.PSPath
        Write-Host "Registry InstallLocation: $($p.InstallLocation)"
        Write-Host "Registry UninstallString: $($p.UninstallString)"
    }

# === 步驟 3：環境變數審計 ===
[Environment]::GetEnvironmentVariables("User") | Where-Object { $_.Key -like "*$appName*" }

# === 步驟 4：第三方工具衝突 ===
# 手動確認：有沒有 proxy/hook/switch 工具安裝？
# 例：cc-switch, proxifier, etc.

# === 步驟 5：搬移 + Junction ===
Move-Item $srcPath $dstPath
New-Item -ItemType Junction -Path $srcPath -Target $dstPath

# === 步驟 6：修復所有參考點 ===
# 6a. 修捷徑
Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu" -Recurse -Filter "*$appName*.lnk" | ForEach-Object {
    $lnk = $sh.CreateShortcut($_.FullName)
    $lnk.TargetPath = $lnk.TargetPath -replace [regex]::Escape($srcPath), $dstPath
    $lnk.Save()
}

# 6b. 修 Registry
$key = Get-ChildItem "HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall" |
    Where-Object { (Get-ItemProperty $_.PSPath).DisplayName -like "*$appName*" }
Set-ItemProperty $key.PSPath -Name "InstallLocation" -Value $dstPath

# === 步驟 7：立即啟動驗證（5 分鐘內）===
Start-Process (Join-Path $dstPath "Application\$appName.exe")
# 確認：App 正常開啟？核心功能正常？
# 失敗 → 立刻還原備份，不要繼續診斷
```

### NEC
① 聽到「搬 D 碟」 → 問清楚哪些 App
② 一次只搬一個 App
③ 七步驟缺一不可
④ 搬完 5 分鐘內測試
⑤ 失敗立刻還原，不超過 5 分鐘的診斷就告知教練

`7ed5b9ce`（Comet 修復）

## 📍 案例 W02：外接硬碟每次都要手動指派磁碟代號，USB隨身碟正常（2026-07-07）

### 事件
教練外接 2.5 吋硬碟（不論 SSD 或 HDD）都無法自動出現在「本機」，每次都要進「磁碟管理」手動「變更磁碟代號及路徑→新增」才會出現。但 USB 隨身碟插上完全正常、自動出現。

### 排查過程（一步步排除，不是憑猜測直接下結論）
1. 先查 `diskpart` → `automount`：確認是「已啟用」，排除全域 automount 被關閉
2. 再查 `Get-Disk` / `list disk`：磁碟狀態都是 Online、Healthy，排除離線或磁碟簽章衝突
3. 再查 `select partition` → `attributes volume`：確認 `No Default Drive Letter: No`，排除該磁區被標記「不給預設代號」
4. 教練提供關鍵線索：**不管換哪一顆 2.5 吋外接盒都一樣要手動指定，USB 隨身碟完全不會**——這才是抓到真正病根的關鍵一句話

### 根因
USB 隨身碟在 Windows 底層被識別為「抽取式媒體（Removable）」，插上必定自動指派代號。
2.5 吋外接盒（不論內裝 SSD 或 HDD）透過 USB-SATA 橋接晶片連線時，Windows 通常辨識成「固定磁碟（Fixed）」（`Get-Volume` 的 `DriveType` 欄位可驗證）。Fixed 類型磁碟是否自動掛載，仰賴系統的掛載點資料庫（Mount Manager / MountedDevices）比對磁碟識別碼——便宜/雜牌橋接晶片如果沒有每次回報一致的裝置序號，Windows 就會判定「這是新磁碟」，而新的 Fixed 磁碟預設不會自動給代號。

### ✅ 正確 SOP
以系統管理員權限執行：
```
diskpart
automount scrub
automount enable
exit
```
接著**務必重新開機**（不重開機不會生效），開機後插上外接硬碟測試是否自動出現代號。

教練這次照此步驟操作後，重開機測試成功，確認可正常讀取。

若重開機後仍無效 → 判定為外接盒/橋接晶片本身的限制，系統設定無法根治，長期解法是更換支援 UASP、知名橋接晶片（如 ASMedia 235/236 系列）的外接盒。

### NEC（排查順序，不要跳步、不要一開始就猜是硬體壞了）
① 先查 `automount` 有沒有被關（十之八九不是這個，但成本最低，先排除）
② 再查 `Get-Disk` 是否 Offline
③ 再查該磁區 `attributes volume` 的 `No Default Drive Letter`
④ 都排除後才是「`automount scrub` + 重開機」
⑤ 若確認「只有 2.5 吋外接盒異常、隨身碟正常」→ 直接指向 Fixed vs Removable 掛載邏輯差異，不用再繞其他方向猜

### 適用範圍
- ✅ 聯想（Lenovo）Windows 11 Pro for Workstations 電腦上實測有效
- ⚠️ 蘋果電腦（macOS）較少出現此問題（外接硬碟辨識/掛載機制不同），此 SOP 主要給 Windows / 聯想電腦使用，Mac 端遇到同類抱怨時不要照搬這套 diskpart 步驟

（本次為 Windows 端會話直接修復，無獨立 commit，記錄於本篇 SOP 本身）

## 📍 案例 W03：Windows App「主程式留C、增量搬D」完整生命週期 SOP（2026-07-08 宏碁機驗證）

**適用情境：** 全新一台 Windows 電腦，要把 LINE / Zoom / Comet / Chrome 這類會不斷長大的 App 資料搬到第二顆硬碟省空間，同時保證 App 不會壞。
**本篇定位：** 整合案例30（血淚教訓）+ W01（七步驟審計）+ `claude-brain/project_line_moved_to_e.md`（LINE版本陷阱）+ 案例39（穩定後清理）成一份「從裝機當天到長期維護」都能照做的完整流程。**任何一台新機器要做同樣的事，讀這一篇就夠，不用再去湊散落各處的舊案例。**
**跨機驗證：** 宏碁筆電（本機，D 槽）＋ 聯想筆電（TREE，E 槽）皆已用本流程跑過，結論一致。下方指令一律用 `$TargetDrive` 代表目的地磁碟代號，執行前依實際環境改成 `D:` 或 `E:`。

### 為什麼不能用「整包資料夾 Junction」抄捷徑（先讀這段，不要跳過）

- **案例30教訓**：整包 junction 搬 Comet／Claude Desktop，捷徑與 Registry 仍指向舊 C 碟路徑，導致 Claude Desktop 全損、Comet 損毀，燒了教練 4 小時。
- **LINE 版本陷阱**：LINE 新版 LineLauncher.exe 會用 `GetModuleFileName()` 比對自己實際路徑跟 Registry 的 `LauncherPath` 是否一致，整包 junction 後路徑對不上，直接報「Invalid launcher path」拒絕啟動；LINE 舊版（無此驗證）才會整包搬也沒事。**不能預設每個 App 都跟舊版 LINE 一樣安全，一律當作「有驗證」處理最保險。**
- **正確原則只有一條**：找出 App 資料夾裡「含執行檔／安裝資訊」的子資料夾（一定留在 C 碟原地），跟「純使用者資料，只會被讀寫、不含 exe」的子資料夾（這部分才搬去 `$TargetDrive`），兩者分開處理，永遠不要整包搬。

### Phase 1：全新機器首次搬移（每個 App 照這個順序，一次只搬一個）

```
Step 0　確認 App 目前能正常開啟，關閉它：Stop-Process -Name <ProcessName> -Force
Step 1　判斷「主程式子資料夾」vs「資料子資料夾」（見下方對照表；沒有前例的新App，
        用 Get-ChildItem 找哪個子資料夾裡有 .exe，那個留 C，其餘才是資料候選）
Step 2　捷徑審計：Get-ChildItem Desktop, Start Menu -Recurse -Filter *.lnk，用
        WScript.Shell 讀 TargetPath，確認每個捷徑都只指向「主程式子資料夾」內的
        exe，不會指到即將搬走的資料子資料夾
Step 3　Registry審計：HKCU:\...\Uninstall 找 InstallLocation / UninstallString，
        確認同樣只指向主程式子資料夾
Step 4　環境變數審計：[Environment]::GetEnvironmentVariables("User") 有沒有跟這個
        App相關的路徑變數
Step 5　第三方工具衝突檢查（有沒有 proxy/hook/switch 類工具可能干擾這個App）
Step 6　robocopy 資料子資料夾到目的地（絕對不要用 Move-Item 或 Copy-Item 處理大量
        小檔案，會漏檔）：
        robocopy "<來源>" "$TargetDrive\Claude-Data\<App>-<用途>" /E /COPY:DAT /R:1 /W:1
        跑第二次 /MIR 確保無殘留，並比對來源/目的地「檔案數＋總大小」差異必須為 0
Step 7　原資料子資料夾 Rename 成 <原名>.stale_backup_YYYYMMDD（不要刪、不要直接
        砍掉重練），確認 Rename 成功後才建 Junction：
        New-Item -ItemType Junction -Path "<原路徑>" -Target "$TargetDrive\Claude-Data\<App>-<用途>"
Step 8　立即開啟App，5分鐘內驗證核心功能正常（登入、資料讀得到）。失敗 → 刪掉
        Junction、把 .stale_backup 資料夾改回原名，不要診斷超過5分鐘，先讓App恢復
        正常再回頭查原因
```

### 已知 App 對照表（本機 + 聯想機實測，新機器可直接套用，不用重新審計）

| App | 主程式子資料夾（留C）| 資料子資料夾（搬 `$TargetDrive`）| 已知陷阱 |
|---|---|---|---|
| **LINE** | `AppData\Local\LINE\bin`（含 LineLauncher.exe） | `Cache`、`Data` 兩個都要搬，各自獨立 Junction | 新版LineLauncher會驗證啟動路徑，**絕對不能連`bin`一起搬**；舊版（9.x左右）較寬鬆但仍建議統一走這套安全做法 |
| **Zoom** | `AppData\Roaming\Zoom\bin`（含Zoom.exe）＋`uninstall`（留C，很小不用搬）| `data`、`logs`、`reports` 三個資料夾各自獨立 Junction | 無 |
| **Comet（Perplexity）** | `AppData\Local\Perplexity\Comet\Application`（含comet.exe）＋`Temp`（留C，很小）| `User Data` | 案例30就是死在把`Application`一起搬走，這次只搬`User Data`後兩台機器都驗證正常 |
| **Google Chrome** | `AppData\Local\Google\Chrome\Application`（若為使用者層級安裝；系統層級安裝則exe在`C:\Program Files\Google\Chrome`，完全不受影響）| `User Data`（Chrome本身設計就是資料與程式分離，`User Data`底下不含執行檔，相對安全）| 無 |

### Phase 2：觀察期（搬移後 7 天內，鐵律不可打折）

- 🔴 **`.stale_backup_YYYYMMDD` 資料夾 7 天內絕對不能刪**——這條鐵律是用教練「LINE 4GB 聊天記錄永久遺失」換來的（見 `claude-brain/project_line_moved_to_e.md`），沒有雲端備份能救，刪了就是真的沒了
- 期間順手用 `Sort-Object LastWriteTime -Descending` 確認 Junction 目標資料夾持續有新寫入，這是「資料是活的」唯一可信證據，不能只看 Junction 存在就結案

### Phase 3：穩定後清理（案例39原始流程 + 這次新學到的擴充判斷法）

```
Step 1　全機掃描找孤兒資料夾，不要只找教練點名的那一個：
        Get-ChildItem "$TargetDrive\Claude-Data" -Directory |
          Where-Object { $_.Name -match '\.stale_backup(\.|$)|\.bak(\.|$)|-Local$' }
        🆕 這次新學到：孤兒資料夾不一定都帶日期後綴（例如這次發現的
        Google-Chrome-Local，是搬家方法改良前留下的整包舊鏡像，沒有.stale_backup
        字樣）。判斷「是不是孤兒」的準則不是看名字，是看：現役App在C槽的資料夾
        裡，有沒有任何子項目的 Junction Target 指向這個候選資料夾？沒有任何連結
        指向它 → 才是可清的孤兒
Step 2　對每個候選，確認：① 已超過7天保留期 ② 對應的現役資料已用「近期有無寫入」
        驗證是活的，兩者都成立才列入可刪清單，缺一律先擱置
Step 3　列出路徑＋大小給教練看過一遍，教練口頭明確說「刪」才執行
Step 4　用 Safe-Remove（`scripts/delete_guard.ps1`）刪除，🔴禁止直接呼叫
        Remove-Item -Recurse -Force：
        New-Item -ItemType File -Force "$env:USERPROFILE\.openclaw\workspace\state\DELETE_APPROVED"
        . "$env:USERPROFILE\Documents\mac-openclaw-workflows\scripts\delete_guard.ps1"
        Safe-Remove -LiteralPath "<絕對路徑>" -MaxGB <無條件進位的實際GB數> -Recurse
        🆕 **技術陷阱（這次才發現）**：`delete_guard.ps1` 檔案是 UTF-8 無 BOM 編碼，
        在 Windows PowerShell 5.1（非 pwsh 7）下用系統內建的 `.` 直接載入，中文字串
        會解析失敗、整個腳本 ParseException，`Safe-Remove` 函式根本沒被定義出來。
        必須先轉檔加 BOM 再載入：
        ```powershell
        $src = "$env:USERPROFILE\Documents\mac-openclaw-workflows\scripts\delete_guard.ps1"
        $fixed = "$env:TEMP\delete_guard_bom.ps1"
        Get-Content -LiteralPath $src -Raw -Encoding UTF8 | Set-Content -LiteralPath $fixed -Encoding UTF8
        . $fixed
        ```
Step 5　刪除後立刻驗證：Test-Path 必須回傳 False，並用 Get-Volume 比對刪除前後
        SizeRemaining 差異，數字要對得上
Step 6　請教練實際重開每個受影響的App，肉眼確認功能正常，不能省略
```

### 🆕 語音輸入新陷阱（追加進案例8的清單）

教練這次口語說「C槽的Cloud Data」，實際是語音辨識把「**Claude-Data**」聽成「Cloud Data」，而且教練自己也把「C槽」「D槽」說成「西潮」「低潮」。**判斯準則：教練說的資料夾名字，如果字面上在C槽/系統資料夾裡查不到、但發音很接近D槽已知的資料夾名，且教練當下語境是在講D槽的東西，優先懷疑是語音辨識誤植，主動覆述確認，不要照字面去 C 槽亂找或亂刪。**
