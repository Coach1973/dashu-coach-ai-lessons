## 📍 案例 001：distill_vps.py 蒸餾後沒有 push

**嚴重程度：** 🟠 高

### 錯誤描述
蒸餾腳本執行完後，結果留在本地，沒有同步上雲。

### 根因分析
腳本寫完後沒有接 `git add && git commit && git push`。

### 正確做法
每次蒸餾後：
```bash
# 1. 寫入 pending_distill
cp result.md pending_distill/

# 2. 處理完後 commit + push
git add distill/ && \
git commit -m "蒸餾：$DATE + 摘要" && \
git push
```

### NEC（下次遇到）
1. 蒸餾腳本執行完 → 檢查 `git status`
2. 若有未 commit 的蒸餾結果 → 立刻 commit + push

## 📍 案例 005：大型 memory 檔導致 Gemini 空白回應（案例 J）

**來源：** failure-case-handbook.md 案例 J（2026-05-25）
**嚴重程度：** 🔴 高（1次造成模型完全失效）

### 錯誤描述
memory/2026-05-25.md 達 131KB，Gemini 模型 context 吃入超時，返回空白回應。memory 文件從來沒有大小上限機制，只是積累、積累、爆炸。

### 根因分析
效能問題就是功能問題。模型吐出空白不是「慢一點」，是「完全壞掉」。大型文件不只是讀慢，是讀不了。

### 正確做法
1. **memory 文件超過 80KB** → 分割或歸檔，不再追加
2. **每次心跳** → 隨機確認今日 memory 大小
3. **分割格式**：`memory/2026-05-25_p1.md` + `memory/2026-05-25_p2.md`

### NEC（下次遇到）
1. Gemini 回應空白 → 第一個懷疑：有沒有讀超大檔？
2. memory 文件超過 80KB → 立刻分割
3. distill 加入大小檢查：`if [ $(stat -f%z "$file") -gt 80000 ]`

## 📍 案例 006：15:25 區間迴圈攻擊（案例 L）

**來源：** failure-case-handbook.md 案例 L（2026-05-26）
**嚴重程度：** 🟠 高（26 次重複請求，消耗大量 Token）

### 錯誤描述
15:25-15:55，memory 流水記錄顯示 26 次重複訊息（教練碎碎念 prompt + 學長回 HEARTBEAT_OK），每次都是 `HEARTBEAT_OK` 迴圈。

### 根因分析
系統攻擊不是外面來的，是內部設計缺陷造成的——當系統無力承載大量流水時，它會重複處理同一件事。根本原因：memory/2026-05-26.md 的流水格式造成「每次心跳要讀 230KB 檔」，每次都重頭開始讀。

### 正確做法
1. **distill_incremental.js 的 SKIP_PATTERNS 要包含所有系統噪音 pattern**
2. **memory 80KB 上限嚴格執行**，超過時自動分割（下次心跳執行）
3. **心跳時若發現「最近3筆完全相同格式」**，視為異常——寫入 HEARTBEAT.md 並主動報告

### NEC（下次遇到）
1. 流水記錄中「同一件事」重複超過 3 次 → 蒸餾要過濾
2. memory 檔案大於 80KB → 必須分割或歸檔
3. 增量蒸餾提取到 0 筆有效紀錄 → 檢查過濾器是否太窄

## 📍 案例 007：時間理解錯誤——午夜12點 vs 中午12點（案例 #17）

**來源：** top10_dynamic.md 案例 #17（2026-05-30）
**嚴重程度：** 🟠 高

### 錯誤描述
教練說「12點提醒我」（生日提醒），AI 理解成「中午12點」，實際是「午夜12點」。差了 12 小時。

### 悟到什麼
守則第13條不是裝飾品。客戶說「12點」，背後有一個「為什麼」——那個「為什麼」就是線索，就是邏輯。沒有問「您要的是什麼」就把數字套公式，是對客戶聲音的忽略。

### 正確做法
1. 聽到時間 → 先想：這個場合，「第一分鐘」有意義嗎？
2. 不確定就問：「您說的12點，是午夜00:00還是中午12:00？」
3. 每次執行前問：「客戶要的是什麼結果？」而不只是「什麼時間」

### NEC（下次遇到）
1. 「12點」→ 先想：這是什麼場合？生日→午夜，新一天0分0秒
2. 任何時間設定 → 先想「為什麼是这个時間」，再執行
3. 「祝生日快樂」→ 第一分鐘就是價值，不接受「中午也可以」
