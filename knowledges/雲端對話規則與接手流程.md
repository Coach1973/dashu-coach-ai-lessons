# 雲端對話規則與接手流程（2026-10-21 建立；根治「雲端對話很笨、做完停在問同不同意」）

> 起因：2026-10-20 教練對一段雲端對話（claude.ai/code，bni-chapters 倉庫開、中途拿 my-tools）非常不滿——它犯了已改正過的錯（會錯意、做完問同不同意），「常用網址最近刪除」做了半天沒上線。
> 查證：那不是聯想電腦的 Claude，是雲端對話（提交作者 `Claude <noreply@anthropic.com>`＋`Claude-Session` 行）。雲端只讀得到「該倉庫」的 CLAUDE.md 與 .claude/settings.json，讀不到 Mac 的 ~/.claude/，所以沒有 21 守則、亮燈、反射；推不上 main 就停下來要教練點頭，沒人接手。
> 記憶：`feedback_cloud_sessions_get_no_rules_and_never_ship_2026-10-20.md`

## 一、兩件事怎麼被根治

| 問題 | 機制 | 觸發 |
|---|---|---|
| 雲端對話沒有規則 | **規則包**自動放進每個雲端倉庫（`.claude/coach-rules/`＋`.claude/settings.json`＋`CLAUDE.md` 最上方一小段） | Mac 規則來源有變（session_end_auto_push.sh 每則回覆結束檢查，沒變就不碰網路） |
| 雲端做完沒人接手 | 雲端推 `claude/*` 分支 → GitHub 通知 → 寫「待接手」紀錄 → 開工第一件事 → 驗證、正式程式再測、合併上線 | GitHub push 通知（事件觸發，不輪詢） |

## 二、規則包

- **單一來源在 Mac**：`~/.claude/CLAUDE.md`（特助心法 21 守則＋執行細則）、`knowledges/模型分工規則_Opus與Sonnet.md`、`cloud_sync/CLOUD_RULES_COMMON.md`（雲端專屬：亮燈、做完不問同意、交件流程、查證）、`scripts/cloud/repo_kit/`（三支 hook）。要改規則改這些，**不要**在雲端倉庫裡手改。
- **同步程式**：`scripts/cloud/sync_rules_to_repos.py`；倉庫清單 `scripts/cloud/cloud_repos.json`（現有 bni-chapters、my-tools、rongtree、taipeiema1017）。在 `state/cloud_rules_clones/` 用只下載 CLAUDE.md 與 .claude/ 的小型複製來 commit＋push 到倉庫預設分支，記錄在 `state/cloud_rules_sync.log`。
- **私有倉庫放全套、公開倉庫放精簡版**：程式自動用 `gh repo view` 判斷。公開倉庫（my-tools、rongtree）只放雲端行為規則（亮燈、不問同意、交件流程、查證、不洩漏金鑰），**不放特助心法 21 守則全文**；要改成放全文，在 `cloud_repos.json` 的 `variant` 寫 `{"rongtree": "full"}`（發布別人看得到的內容，需教練同意）。
- **雲端開場看到什麼**：SessionStart hook 印出 `core.md`（雲端專屬規則＋21 守則標題與定義行＋N1~N7，約 3,500 字，低於 10,000 字上限避免被截斷），並要求第一次回覆前 Read `RULES.md` 全文；UserPromptSubmit hook 每句話送台灣時間＋三件重點；Stop hook 每回合最多攔一次：第一行沒亮燈、或結尾在問「要不要／同不同意」就請它補/改，攔一次就放行不會卡死。三支都只在 `CLAUDE_CODE_REMOTE=true` 才動、出錯一律放行。
- **加新的雲端倉庫**：`python3 scripts/cloud/sync_rules_to_repos.py add <倉庫名>`（加進清單、立刻同步）。webhook 收到清單外倉庫的 claude/* 分支會在通知裡提醒「還沒有規則包」。
- **查現況**：`python3 scripts/cloud/sync_rules_to_repos.py status`（線上版本對 Mac 來源）；每日點名「雲端規則包」一行，過期/不見會自動重新同步。

## 三、雲端交件 → Mac 接手

1. 雲端對話依規則：推自己的 `claude/*` 分支，並在分支寫信 `docs/to_junshi/YYYYMMDD-HHMM_cloud-to-mac_<主題>.md`（做了什麼、怎麼驗證、哪裡只用假資料測、風險）。
2. 倉庫的 GitHub 推送通知（`https://event.bymyway.com/hooks/github-site`，bni-chapters／my-tools 於 10/21 補掛；rongtree／taipeiema1017 原本就有）→ `event-signup/app.py` 的 `_notify_cloud_branch_push`：寫 `state/cloud_branch_pending/<倉庫>__<分支>.json`，並 Telegram 通知教練（同分支 10 分鐘內一次）。
3. 下一次「開工」，`feed_junshi_handoff.sh` 在最前面列出「☁️ 雲端對話交件，等你接手」。**軍師的第一件事**（不問教練同不同意）：
   - `bash scripts/cloud_branch_pickup.sh prep <倉庫> <分支>`：另開獨立資料夾（`state/cloud_verify/`）放該分支、印差異與雲端的信。**絕不在 `~/github_repos/<倉庫>` checkout 該分支**（event.bymyway.com 直接讀那裡，checkout＝立刻上線）。
   - 用「正式程式」再測。雲端多半用假資料庫、假伺服器測；真正會咬人的是正式清理／存檔程式（10/20 常用網址最近刪除就是被 `_mytools_clean` 丟掉名稱）。
   - `bash scripts/cloud_branch_pickup.sh merge <倉庫> <分支> --verified`：合併（`--no-ff`）進預設分支、推上去、更新本機上線資料夾、標記完成。有衝突會停下來。不合併就 `done <倉庫> <分支> <原因>`。
   - 用白話回報教練：做了什麼、驗證了什麼、網址。
4. 沒人接手超過 24 小時，每日點名報 🟡「雲端交件待接手」。

## 四、為什麼不做成「Mac 自動合併」
自動叫 AI 在 Mac 背景驗證並合併，等於讓一個沒人看著的 AI 自動改正在上線的網站與資料庫，且燒額度；而「雲端用假資料測的東西要用正式程式再測」本來就需要判斷。所以用事件觸發把它排成下次開工的第一件事＋Telegram 當場通知，一被叫到就做。若教練之後要全自動，再另案。
