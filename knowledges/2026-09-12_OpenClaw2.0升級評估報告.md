# OpenClaw 2.0（2026.8.1）升級評估報告

## 給教練的一句話結論

**現在先不要升級到2.0。但可以先做一次「低風險小維護」——把版本從6.34補到6.35（這是教練現在這條安全路線的最後一版，之後這條路線就不會再更新了）。真正的2.0是換到另一條完全不同的路線，需要先解決兩個具體技術缺口（電腦裡的Node.js版本不合格、5個AI人設共367MB的真實對話記錄要先備份好），時間點抓在教練不忙、可以容許出狀況的空檔再做，且要先在教練另一台不對外服務的電腦（例如聯想或ACER）上先跑過一次。**

以下是完整的查證過程與細節，供教練參考，也留給之後實際動手升級的人（可能是另一位AI）照著做，不用重新查一次。

## 一、這次2.0版本到底改了什麼（白話5條重點）

1. **對話記錄的存放方式要換一種資料庫**：以前教練跟AI講過的每一句話，是一行一行文字檔案存在硬碟裡；2.0之後改存進一種叫SQLite的資料庫格式（比較像Excel表格，一格一格有結構，比較好搜尋、比較好做「備份快照」）。這件事本身立意良好，但「換一種格式存放」代表舊資料要「轉檔」，轉檔這個動作本身就有出錯風險——尤其教練這台機器已經累積了三年多、5個不同AI人設的真實對話記錄，不是隨便能重新生成的東西。

2. **內建的「OpenProse」小工具直接被拿掉了**：這是官方原本內建的一個文件協作功能（教練這邊完全沒用過，查證後零風險）。官方要教練改用另一套新的技能機制銜接，舊檔案不會不見，只是使用方式要換。

3. **模型路由的命名統一化**：官方自己過去對接ChatGPT/Codex這類模型時，命名一直沒統一（有時叫`codex/xxx`，有時叫`openai-codex/xxx`），2.0之後統一改叫`openai/xxx`。教練主要使用的是MiniMax跟Claude，這件事對教練本人的帳號沒有影響；但查證時意外發現，孔大哥這個AI人設的獨立設定檔裡剛好用到舊的命名方式，升級時要記得處理（詳見第二節）。

4. **新增「多人共用同一個工作階段」的協作功能**：這是2.0最大的新功能之一，讓教練可以在不同裝置間接續同一段工作，或多人一起看同一段對話。但官方自己白紙黑字寫明：**這個功能不是防止互相偷看、互相干擾的「安全鎖」，只是「使用方便」的功能**，設計前提是「單一個人自己使用，底下可能開很多個AI」，不是「開放給互不信任的很多人共用」。教練這台機器背後對接的是BNI真實會員、LINE好友這些外部使用者，這件事需要特別小心，第三節會詳細說明。

5. **這是OpenClaw史上規模最大的一次改版**（16000多個程式修改、900多位工程師參與），新功能非常多，代表能踩到新問題的機率也比過去任何一次升級都高。事實上，官方自己在2026年8月31日發布2.0之後，短短12天內（到本報告撰寫的9月12日為止）就已經連續補了5次小版本（8.2、9.1、9.2、9.3、9.4），代表2.0本身目前仍在快速修正中，還沒完全穩定下來。

## 二、對這台機器的具體風險評估

### 2.0 最重要的一個前提：這次要換的是「另一條路」，不是「同一條路往前一步」

這是本次評估最關鍵、也最容易被誤會的一點，要先講清楚：

教練這台Mac目前走的是「extended-stable」這條穩定維護路線（半年前就已經拍板走這條路，`scripts/openclaw_upgrade.sh`這支腳本裡寫死鎖定這條路線）。這條路線目前最新版本是**2026.6.35**，2026年9月10日才剛發布，官方原文寫明：「**This is the final June 2026 Extended Stable (LTS) release**」——這是6月這條維護路線的**最後一版**，之後這條路線不會再有新版本了。

也就是說：
- 如果教練現在直接執行現有的`scripts/openclaw_upgrade.sh upgrade`指令，會升級到**2026.6.35**，不會升到2026.8.1（2.0）。這一步風險很低（純安全性/穩定性修補，沒有2.0的任何新功能，也就沒有2.0帶來的新風險），但也是這條路線最後的免費維護機會。
- 若要用到2.0的功能，必須**主動換路線**——從「extended-stable」切換到官方的「latest」（一般穩定線），這是需要教練另外拍板決定的動作，跟過去「同一條路線出新版就升」的邏輯不一樣。

**好消息**：查證確認2026.8.1不是教練過去被提醒過的那種「版號比較大、但發佈時間反而更早」的陷阱版本（例如`2026.7.1-2`那次）。用npm官方資料庫直接查詢，2026.8.1確實是**時間序上**排在2026.6.34之後的正式版本（2026-08-31發布，2026.6.34是2026-08-04發布）。但它跟教練現在走的「extended-stable」是兩條不同的官方維護路線，這是必須先弄清楚的技術前提，不是「數字比較大就直接切過去」。

查證方式（供之後查核用）：
```
npm view openclaw dist-tags
# 目前結果：beta: 2026.9.4 / extended-stable: 2026.6.35 / latest: 2026.9.4
```

### 🔴 重要發現：孔大哥AI人設的獨立設定檔用到了舊版`codex`命名

全機搜尋`OpenProse`跟`codex`字樣後，主設定檔（`openclaw.json`）跟25支自訂hook都是乾淨的（零命中），但在下面這個檔案找到真實命中：

**檔案：`/Users/bymyway/.openclaw/agents/kong/agent/models.json`**（這是孔大哥這個AI人設專屬的模型設定檔，**目前不在git版控範圍內**——`git status`顯示`agents/kong/`整個目錄是未追蹤狀態）

```
第81行：    "codex": {
第83行：      "apiKey": "codex-app-server",
第85行：      "api": "openai-codex-responses",
第90行：          "api": "openai-codex-responses",
第112行：          "api": "openai-codex-responses",
第134行：          "api": "openai-codex-responses",
```

這個設定檔定義了一個名稱叫`codex`的provider，內含3個模型（gpt-5.4、gpt-5.4-mini、gpt-5.2），API類型是`openai-codex-responses`。從孔大哥的歷史對話紀錄（`agents/kong/shared-relay/bot_chat_2026-02-25_result.json`）可以看到，這個設定過去真的被實際呼叫過，而且發生過「OAuth token過期需要重新授權」的錯誤（`OAuth token refresh failed for openai-codex`），也曾經手動切換過模型顯示成`openai-codex/gpt-5.4`這種格式。

官方2.0公告原文寫的是：「使用`openclaw doctor --fix`來把出廠內建的`codex/*`跟`openai-codex/*`模型參照、provider設定、已存的session、自動化路由，全部遷移成`openai/*`」——**但這句話講的是「出廠內建」的部分，孔大哥這個設定檔是教練自己另外寫的自訂provider，不確定`doctor --fix`會不會掃到、會不會正確處理**。

風險等級：🟡 **需要小改（且需要人工複查）**——升級後務必手動打開這個檔案，確認`codex`這個provider有沒有被自動更名、模型呼叫還能不能正常運作，不能只看主設定檔的健檢結果就以為沒事。

### `scripts/openclaw_upgrade.sh` 升級腳本：架構堪用，但要補強3點才能真正用來升2.0

這支腳本是教練team在6.33→6.34小版本升級時寫好、也實際用過的四階段流程（`check` / `upgrade` / `verify` / `rollback`），架構設計得不錯——會自動備份設定檔、有5項健檢（外掛數量/hook載入數/Telegram連線/排程狀態/報名端點），失敗時有現成的一鍵回退指令。

但如果要拿來升級到2.0，需要補強：

1. **`TARGET_TAG="extended-stable"`寫死了目標路線**——如前面說明，這個設定只會帶教練到2026.6.35，到不了2.0。若要升2.0，必須改成**明確指定的版本號**（例如寫死`"2026.8.1"`），**不建議直接改成`"latest"`**——因為`latest`這個標籤是會一直往前跑的活動標籤，查證當下（2026-09-12）`latest`已經指向`2026.9.4`，比2026.8.1這個「2.0」本尊還多跳了4次小版本，用`latest`會在教練不知情的狀況下多升好幾版。

2. **`cmd_verify`裡「基準48啟用」這個數字是寫死的**——這是6.34時代的基準值，2.0如果外掛清單真的有變動（前面比對出的mistral/meta/imessage/opencode四項），這個健檢會誤判成「外掛數量變少了、出問題了」。升級前應該先用`openclaw plugins list`重新取得當下真實的啟用數量當新基準，而不是沿用「48」這個舊數字。

3. **完全沒有檢查Node.js版本相容性**——這是本次查證新發現、教練原本沒有預期到的一個技術缺口，非常重要，獨立說明如下。

### 🔴🔴 新發現的技術缺口：這台Mac現有的Node.js版本，裝不上2.0

用npm官方資料庫直接查詢三個版本各自要求的Node.js版本（`engines`欄位）：

| OpenClaw版本 | 要求的Node.js版本 |
|---|---|
| 2026.6.34（教練現在用的） | `>=22.19.0`（很寬鬆） |
| 2026.6.35（extended-stable下一版） | `>=22.19.0`（一樣寬鬆） |
| **2026.8.1（2.0）** | `>=22.22.3 <23` 或 `>=24.15.0 <25` 或 `>=25.9.0`（**三選一的精確區間**） |

這台Mac目前透過Homebrew安裝的Node.js版本是**v25.6.1**——查證後發現這個版本**三個區間都對不上**：不是22.x系列、不是24.x系列，也還沒到25.9.0這條線（25.6.1 < 25.9.0）。

也就是說：**如果現在直接對這台Mac執行`npm install -g openclaw@2026.8.1`，很可能在安裝當下就跳出Node版本不相容的警告，就算裝上去了，服務本身也有起不來的風險**。

進一步查證Homebrew目前能裝到的Node版本：`node`套件是25.6.1（不符合）、`node@22`套件是22.22.0（也還差一點點沒到22.22.3的門檻）。也就是說**截至查證當下，Homebrew現成能裝的版本都還沒有一個真正符合2.0要求**，需要用`nvm`這類工具另外裝一個精確符合區間的版本，或是等Homebrew之後更新套件版本再確認一次。

這件事沒有先查清楚就動手升級，很可能不是「升級失敗、退回原狀」這麼簡單，而是直接把24小時服務中的Gateway打掛。**這是動手升2.0之前，必須第一個解決的技術關卡**。

### Session儲存機制（改用SQLite）：目前真實對話記錄放在哪裡、規模多大

查證這台機器目前「對話記錄」的實際存放位置，發現5個AI人設**各自獨立**存放，全部都是逐行文字檔（`.jsonl`）格式，**不是**SQLite：

| AI人設 | 對應服務 | 檔案數 | 佔用空間 |
|---|---|---|---|
| `agents/main/sessions/` | 教練本人＋Telegram/LINE群組 | 3,108個檔案 | 217 MB |
| `agents/peipei/sessions/` | 佩佩老師AI人設 | 171個檔案 | 91 MB |
| `agents/jiaolian_thoughts/sessions/` | 「教練都在想什麼」LINE帳號 | 147個檔案 | 31 MB |
| `agents/bni_tainan/sessions/` | BNI大台南小幫手LINE帳號 | 112個檔案 | 21 MB |
| `agents/kong/sessions/` | 孔大哥AI人設 | 32個檔案 | 7 MB |
| **合計** | | **約3,570個檔案** | **約367 MB** |

這些就是官方2.0公告裡說「舊版session格式要遷移到SQLite」所指的東西。官方文件也特別提醒：**升級後如果要退回1.x舊版本，這些SQLite格式的資料需要「手動轉換」才能還原成舊格式，不是點一下rollback指令就能自動復原**。

另外查到兩個看起來相關但其實是舊/次要資料的路徑，一併說明避免混淆：
- `~/.openclaw/workspace/sessions/`：只有3個jsonl檔+1個sessions.json，最後修改時間停在7月8日，看起來是main agent早期的殘留格式，並非目前實際在用的即時儲存位置。
- `~/.openclaw/workspace/claude-sessions/`：4份`.md`格式的人工/自動摘要檔，是「總結」而非原始逐字對話記錄。
- `~/.openclaw/state/openclaw.sqlite`（6MB，今天才修改過）：這是Gateway本身內部運作用的資料庫（跟排程、外掛狀態有關），**這個檔案在6.34版就已經是SQLite格式，跟2.0要遷移的「對話session」是兩件不同的事**，這裡先說明清楚避免誤會「反正已經是SQLite了應該沒差」。

風險等級：🔴 **有風險，需要仔細測試**——這不是可以「重新設定一次」找回來的東西，是5個AI人設三年多累積下來的真實對話記憶，一旦轉檔過程失敗或不完整，很可能是不可逆的資料損失。

**建議**：升級前，除了`openclaw.json`本身，上述5個`agents/*/sessions/`資料夾（總計約367MB）都要完整備份一份，而且**建議備份到這台Mac以外的地方**（例如VPS或外接硬碟），不要只放在同一顆硬碟裡就以為安全。這台Mac硬碟目前還有63GB可用空間（總容量228GB、已用16GB），備份完全沒有空間問題。

## 三、安全疑慮說明：共享session功能，先不要開

2.0最大的新功能之一是「多人共用/跨裝置接續同一個工作階段」。查證官方自己的安全文件（`SECURITY.md`）後，官方原文非常明確地寫：

- session識別碼（sessionKey）只是「路由用」的，**不是**「誰能看誰不能看」的授權邊界。
- session的擁有者、可見度、在場狀態，是「使用方便」的功能，**不是**安全邊界。
- 官方直接定義自己的安全模型是「個人助理模式」（一個受信任的操作者，底下可以有很多個AI），**不是**「可以讓互不信任的很多人共用同一個系統」的多租戶模式。
- 官方甚至白紙黑字建議：如果真的有互不信任的人要共用，正確做法是「各自開一個獨立的Gateway」，最起碼也要用不同的作業系統帳號、不同的機器，而不是共用同一個。

除了官方自己承認之外，也查到多家第三方媒體（VentureBeat、Dataconomy等）跟一篇獨立的資安研究論文，都獨立提出同樣的結論：2.0預設情況下，沙箱隔離跟執行前的核准機制是關閉的；密鑰儲存庫（存放API金鑰、密碼那種）本身**不會加密**，只靠檔案系統的權限做保護。

**誠實說明一件事**：教練原本提供的資訊說這個結論來自「The Register」這家媒體，我實際查證後，**沒有找到The Register刊登這篇報導的原始出處**，無法證實「The Register」這個媒體名稱本身。但同樣的結論（共享session缺乏網路層/檔案系統層的安全邊界）在OpenClaw官方自己的SECURITY.md、以及VentureBeat、Dataconomy等其他媒體報導中都得到獨立確認，**結論本身查證屬實**，只是「The Register」這個具體出處我沒能核對到，在此如實註記，不假裝查到了。

**對教練這台機器的實際意涵**：這台Mac不是只服務教練一個人——背後接了BNI大台南小幫手（真實BNI會員在用）、教練都在想什麼（真實LINE好友在用）、孔大哥、佩佩老師，共4個對外服務的AI人設。如果升級後不小心打開「共享session」讓別人加入教練自己的工作階段，等於把教練的密碼、API金鑰、私人對話，暴露在一個「看起來像獨立房間、其實沒有真正隔離」的共用空間裡——這正是官方文件警告的情境。

**建議**：即使決定升級到2.0，這個共享session功能**維持關閉、不啟用**，除非教練未來有「自己一個人在Mac跟手機之間接續同一段工作」這種純單人跨裝置的需求，且屆時要再三確認加入的都只有教練自己的帳號。

## 四、建議：現在升級 / 再觀察 / 分階段升級

三個選項逐一評估，基於實際查到的資訊，不是套用空泛的「等社群踩雷」說法：

**❌ 現在立刻升級到2.0：不建議。**
理由：①Node.js版本現在就對不上，會卡在安裝這一關，貿然執行有打掛服務的風險；②距離2.0發布只有12天，官方自己都還在連續補丁（8.2、9.1、9.2、9.3、9.4，平均不到3天一次），代表2.0本身還在快速變動中；③現有的`openclaw_upgrade.sh`腳本目前設定的目標路線（extended-stable）根本到不了2.0，直接執行反而是升到一個教練沒打算要的版本（6.35）。

**🟡「再觀察一段時間」：部分成立，但要修正——時間已經走了一半。**
教練心法裡「善用他人已驗證的經驗、讓別人先踩雷」的精神是對的方向，但查證發現：2.0發布到今天（2026-09-12）已經過了12天，官方自己都已經發布了5次修補版本，代表最動盪、最不穩定的頭幾天已經過去了。**真正卡住教練的，不是「時間不夠久」，而是兩個具體、可以馬上動手解決的技術缺口**：Node.js版本要先解決、共享session的安全設定要先弄懂並確保維持關閉。單純再等下去不會讓這兩個問題自己消失。

**✅ 建議做法：分兩階段走**

**第一階段（低風險，現在就可以做）**：先用現有腳本把版本從6.34補到**2026.6.35**——這是extended-stable路線的最後一版，純安全性/穩定性修補，沒有2.0的任何新功能也就沒有新風險。因為官方已經明講這條路線不會再更新，越晚做，這台機器在「換到2.0之前」的空窗期就越長、累積的未修補安全性問題就越多。

**第二階段（換路線，需要教練另外拍板，且要先做準備）**：等下面三件事都準備好，再決定要不要換到2.0這條路線：
1. 確認能裝到符合2.0要求的Node.js版本（22.22.3+／24.15.0+／25.9.0+三選一）
2. 367MB的5個AI人設對話記錄，完整備份到這台Mac以外的地方
3. `openclaw_upgrade.sh`腳本按照第五節的補強清單修改完成

而且屆時建議**先在教練另一台不對外服務的機器（例如聯想Windows或ACER）上完整跑過一次流程練習**，確認整個過程順利、5項健檢都能過，再回頭對這台正式服務的Mac動手，不要讓24小時對外服務的機器當「第一次嘗試」的白老鼠。

真的要換路線時，建議**鎖定當下最新的穩定patch版本，而不是死盯著`2026.8.1`這個2.0剛發布的初版標籤**——因為官方後續的8.2/9.1/9.2/9.3/9.4很可能已經修掉2.0剛發布時的早期問題，直接抓最新patch通常比抓最初的2.0本尊更穩。

## 五、如果教練決定升級，具體怎麼做

### 第一步：低風險維護升級（6.34 → 6.35），現在就能做

```bash
cd /Users/bymyway/.openclaw/workspace
bash scripts/openclaw_upgrade.sh check      # 先看現況，不動任何東西
bash scripts/openclaw_upgrade.sh upgrade    # 會自動備份設定檔，再升級到6.35
bash scripts/openclaw_upgrade.sh verify     # 5項健檢：外掛數/hook載入/Telegram/排程/報名端點
```

若`verify`任何一項出現🔴紅字，立刻執行：
```bash
bash scripts/openclaw_upgrade.sh rollback   # 一鍵退回6.34
```

### 第二步：換路線到2.0之前的準備工作（現有腳本做不到，需要人工/軍師另外處理）

1. **檢查並解決Node.js版本問題**：
   ```bash
   /opt/homebrew/bin/npm view openclaw@<鎖定的確切2.0版本號> engines
   brew upgrade node          # 或改用 nvm 裝一個落在區間內的精確版本
   /opt/homebrew/bin/node -v  # 確認真的落在要求區間內才繼續下一步
   ```

2. **備份367MB的真實對話記錄+相關設定檔**，複製一份到VPS或外接硬碟（不是只放同一顆硬碟）：
   ```
   /Users/bymyway/.openclaw/agents/main/sessions/
   /Users/bymyway/.openclaw/agents/peipei/sessions/
   /Users/bymyway/.openclaw/agents/jiaolian_thoughts/sessions/
   /Users/bymyway/.openclaw/agents/bni_tainan/sessions/
   /Users/bymyway/.openclaw/agents/kong/sessions/
   /Users/bymyway/.openclaw/openclaw.json
   /Users/bymyway/.openclaw/agents/kong/agent/models.json
   ```

3. **修改`scripts/openclaw_upgrade.sh`**：
   - `TARGET_TAG="extended-stable"` 改成明確指定的版本號（例如當時最新的穩定patch版本號，不要用`"latest"`）
   - `cmd_verify`裡的「基準48啟用」數字，改成升級前用`openclaw plugins list`重新取得的真實數字

4. **執行升級**：
   ```bash
   bash scripts/openclaw_upgrade.sh upgrade
   ```

5. **升級完成後，額外手動驗證（現有腳本涵蓋不到的部分）**：
   - 執行官方指定的`openclaw doctor --fix`，處理OpenProse清理、`codex/`路由遷移、SQLite session轉檔
   - **手動打開`agents/kong/agent/models.json`**，確認裡面的`codex` provider有沒有被正確處理（這個檔案不在主設定檔範圍內，`doctor --fix`可能掃不到），並實際測試孔大哥這個AI人設還能不能正常回應
   - 抽查至少1~2個`agents/*/sessions/`裡舊的對話紀錄，確認轉檔到SQLite後查得到、內容沒有缺漏
   - 確認「共享session」相關設定維持關閉狀態（第三節說明的安全考量）

6. **跑一次`verify`，5項健檢全過才算升級完成**

7. **若任何一項失敗**：執行`rollback`退回6.35（或原本的6.34）。但要特別注意：**這一步是本次升級最大的不可逆風險點**——官方文件提醒，退回舊版後，已經寫成SQLite格式的新資料，需要「手動轉換」才能被舊版正確讀取，不是點一下就能無痛復原。這也是為什麼強烈建議先在教練另一台非正式服務機器上完整演練過一次的原因。
