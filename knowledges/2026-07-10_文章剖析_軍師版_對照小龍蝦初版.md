## 一、文章原文核心論點（我自己讀完全文的一段話總結）

文章主張 OpenClaw 拒絕 RAG 是**哲學選擇**：RAG 適合「查資料」的 Chatbot，但 OpenClaw 要當「自主代理」，需要每次都從同一個認知基礎出發、能跨檔案推理、人格一致——這些 RAG 的片段式檢索做不到。代價是四個 Token 粉碎來源：①每次讀作業(4,000-10,000 tokens)②記憶檔案膨脹③心跳背景吃 token④工具輸出無上限。另外還講了「記憶刷新機制」（壓縮前先存檔，單次長對話成本 10,000-25,000 tokens）跟「通道隊列」（序列化換穩定性）。安全風險：純文字無加密 + Prompt Injection。結論：「你付的不是 Token 費，是『持續存在』的成本。」

這段跟小龍蝦的摘要方向一致，**沒有理解錯誤**——這點要先肯定。

## 二、我親自查證的技術事實（小龍蝦沒做的部分）

小龍蝦的報告是「憑印象比對」，沒有一項附上查證指令或實測數字。我這次每一條都去挖了真實設定檔跟真實檔案大小，發現三個小龍蝦完全沒抓到、甚至結論可能下反了的差異。

### 發現 1：文章說「OpenClaw 完全拒絕 RAG」，但我們其實已經在跑本機向量搜尋——文章的二分法對我們不成立

查 `openclaw.json`：

```json
"memorySearch": {
  "enabled": true,
  "sources": ["memory"],
  "provider": "local",
  "store": { "vector": { "enabled": true } }
}
```

`provider: "local"` 背後就是本機 ONNX 向量索引（沿革見 `BOT_MESSAGES.md` 2026-06-03 那批對話：原本用第三方 `memsearch` 插件因升級不相容壞掉，後來改走 OpenClaw 內建的向量搜尋，2026-06-16 那次「memorySearch 升級拒付費改本機」的蒸餾場景就是這件事）。

**這代表什麼**：我們不是純 File-First，而是「File-First 當主體 + 語意向量搜尋當輔助工具」的混合架構。文章「RAG vs Full Context 二選一」的框架，套在我們身上是不準的——我們兩個都要，而且是刻意疊加。小龍蝦的報告寫「✅ 我們也別動：守則#02」，等於是**沒發現我們已經動了**，把一個既成事實當成「文章說不用所以我們不用」，這是誤判，不是漏講而已。

### 發現 2：小龍蝦說「我們熱啟動比文章聰明」，但我實測數字比文章講的還高

文章講「單次對話啟動，光是讀作業就要 4,000-10,000 tokens」，小龍蝦的報告寫「✅ 比文章聰明：避免 context 爆」。我實測我們的熱啟動三核心檔案：

| 檔案 | 實際大小 | 粗估 tokens |
|------|---------|------------|
| 特助心法.md | 12,549 bytes | ≈ 6,274 |
| SOUL.md | 18,995 bytes | ≈ 9,497 |
| JUNSHI_HANDOFF_LATEST.md | 5,095 bytes | ≈ 2,547 |
| **合計（軍師版三核心）** | **36,639 bytes** | **≈ 18,318 tokens** |

這已經**超過文章講的「4,000-10,000 tokens」上限**，接近兩倍。小龍蝦沒有實測，直接下「比文章聰明」的結論，是沒查證就下判斷——這正好踩到我們自己守則 #08「引用查證鐵律」要防的坑：說之前沒先查原文/數字。

（補充：這只是「軍師版」三核心，小龍蝦/小龍蝦系統走的是 AGENTS.md 定義的另一套「🔥熱啟動」，理論上有分流減量，但我這次沒有切進小龍蝦的實際 session 去量它的真實熱啟動大小，這點我標注為「未驗證」，不敢跟小龍蝦一樣憑印象斷言。）

### 發現 3：我們自己造了文章完全沒提到的第三個 Token 黑洞——「Dreaming（做夢）」子系統

這是本次最重要的發現，小龍蝦的報告完全沒提到。

實際打開今天的 `memory/2026-07-10.md`（17,073 bytes），前面一大段是系統自動寫入的 `<!-- openclaw:dreaming:light:start -->` ／ `<!-- openclaw:dreaming:rem:start -->` 區塊，內容是像這樣的「候選事實」：

> Theme: `reflections` kept surfacing across 29 memories.
> Assistant: Tonight the archives were full of mirrors — reflections of reflections, the same line numbers surfacing like tide marks on a shore I keep returning to...

我逐段看過，這些內容**大部分是系統在對自己過去產生的「反思」做二次反思**（reflections about reflections），confidence 普遍落在 0.55-0.65，屬於低信度雜訊，不是教練說過的實質內容。今天這個檔案裡，真正的教練對話只有一段（08:18 那句「研究一下那篇文章」），剩下八成篇幅都是這種夢境雜訊。

**更嚴重的是**：我們自訂的「開工六步驟」注入 Hook（`/Users/bymyway/.claude/hooks/feed_junshi_handoff.sh`，75 行）**完全沒有任何字數上限邏輯**——我逐行查過，沒有 `head -c`、沒有 `maxChars`、沒有任何截斷。今天 08:25 我喊「開」的時候，這個 Hook 一次吐出 43.4KB 的內容（含這整包 dreaming 雜訊）直接塞進我的對話——這正是文章警告的「工具輸出無上限」的活教材，而且是**我們自己額外造出來的**，連 OpenClaw 官方原生的 `startupContext.maxTotalChars: 25000`（openclaw.json 裡有這個官方防呆值）都被我們自己的客製 Hook 繞過去了，因為 Hook 走的是 UserPromptSubmit 觸發，不吃原生 startupContext 那條限制。

**這是三個新發現裡 CP 值最高、最該優先處理的一項**：文章講的 4 個 Token 粉碎來源我們大致都比原生版本聰明，但我們自己加蓋的「接力棒 Hook + Dreaming 子系統」疊加起來，反而是我們專屬的、文章完全沒預見到的新粉碎來源。
