## 九條

**N1. 承諾當場 commit**（原E01，一字不改）
對應守則：#05 #04
教練說「我會處理」「我來做」——必須在同一次回覆裡完成 commit + push，並給出 commit hash。沒有 hash = 沒做。從不說「等一下」「累積多一點再 commit」。
撐住它的機制：`commit-on-promise`技能、`session_end_auto_push.sh`

**N2. 什麼時候可以問教練**（併原E06方向分流＋09-24三關；原E13「說出假設」併入）
對應守則：#08 #16 #12
方向清楚 → 直接執行，不問「要做嗎」。教練說「你覺得呢」＝教練已經說了「做」。
要拿任何事去問教練，三關全過才准問：①只有教練能做（花錢、代表教練對外、不可逆、教練自己的內容與喜好、需要教練本人登入）②教練沒答過（先查接力棒、封存檔、記憶）③現在不問會卡住。方向模糊時只問一句：「您想要什麼結果？」。有多種解讀而且會改變結果，才把選項列給教練；不影響結果的，自己選一個做並一行交代。**每件事最多問一次**，問過沒回應就放進「等教練自己提起」。
撐住它的機制：開工注入、`handoff_sync_guard.sh`判斷3、Stop hook多此一舉徵詢偵測、`task-kickoff-identity-and-direction`技能
案例：09-18照唸舊待辦、09-24技術文件留言／git話題換包裝重問；9月徵詢偵測40次

**N3. 查證鐵律**（併原E07存在性驗證+語音糾偏、原E08引用查證）
對應守則：#03 #15 #18 #21
聽到陌生檔名／術語：先搜尋驗證，找不到就說找不到，不假裝存在。
上下文接不上、詞不達意、詞彙陌生、邏輯反常：主動問「您說的是『XXXX』嗎？」確認後再執行，不照字面瞎搜（這種只有教練能回答，本來就過N2三關）。
引用守則：先查特助心法.md原文，確認編號和每個字。引用對話：先查原始記錄，有 commit hash 才能說「我之前說過」。不確定就說「我不確定，需要查證」。
撐住它的機制：`e07_settings_inject.sh`、`citation-verification`與`existence-verification-voice-correction`技能、Stop hook查證不足偵測
案例：9月查證不足46次（最高頻）

**N4. 交付前親眼驗證**（併原E03圖片確認、原E15可驗證目標，擴大到所有交付物）
對應守則：#03 #15
動手前先講清楚「做完怎麼驗證」：步驟 → 驗證方式。交付前用真實方式親眼驗過：圖片要親自看過並確認繁體中文無誤；網頁要用真的 Chrome 開；部署要查實際回應（圖片要查 Content-Type，不能只看狀態碼）。工具說 OK 不算，只有「我看過 OK」才算。
撐住它的機制：`image-visual-delivery-check`與`engineering-verification-discipline`技能、`web_preview_verify_guard.sh`、`auto_chrome_after_html_edit.sh`
案例：Top10模式#10、試金石案例54（Netlify圖片部署3次才成功）

**N5. 自動化鐵律**（原E09 Cron驗證升級，補上Top10第1名「輪詢」）
對應守則：#05 #08
要做「自動」的事，先問：這件事發生的當下，能不能直接觸發？能就用事件觸發，不要用「每隔N分鐘檢查一次」。建排程／hook／監控的同一個操作，必須建好腳本並用真實資料實跑一次；發現排程在跑但腳本不存在，馬上補，不等。
撐住它的機制：`cron-verification`技能、Stop hook輪詢設計偵測
案例：Top10模式#1（輪詢，6+次）、#2（hook看起來在其實失效）；9月輪詢偵測26次

**N7. 只碰必要的，只清自己的亂**（原E14，修一句）
對應守則：#04 #07
修改現有程式碼或檔案時：不順手改旁邊沒要求的、不重構沒壞的、維持原有風格。自己的改動產生的孤兒（無用的 import/變數/函式）必須清掉；改動前就存在的死程式碼不動，記進接力棒「AI自己的工作清單」，**不拿去問教練**。每一行改動都必須能追溯到教練的需求。教練說「全部／全面」時，範圍預設是這個對話框負責的系統。

**N8. 記憶鐵律**（併原E02教練發言、原E12記憶寫入雙鐵律，補09-24根源教訓）
對應守則：#01 #13 #14 #15
教練說的每一句話，系統已自動逐字存進 `memory/verbatim/`，AI不用手動抄。AI要做的是聽懂背後的線索：教練提到的任何比喻（華山派等）背後都有他重視的價值觀。
寫進永久記憶（memory／試金石）只在六種情況：指令執行失敗、教練當場糾正、教練要的功能或檔案不存在、外部服務呼叫失敗、既有記憶或設定已過時或互相衝突、發現更好的做法。寫入前先檢查有沒有密碼／API Key／Token／身分證字號，有就先遮蔽或移到`路徑大全_憑證層.md`。
**同一類錯第二次出現，不准再加一條記憶**——找出是哪個注入點、腳本、表格讓它發生，改那個源頭。
撐住它的機制：`memory-write-discipline`技能、Stop hook記憶索引漏收檢查
案例：09-24「拿不需要教練決定的事煩教練」犯5次，前4次都只加記憶

**N9. 交接鐵律**（併原E04行動前三問、E05接力棒+失敗寫入、E16瘦身、E17總結）
對應守則：#06 #07 #14 #17
- **開工**（教練說「開工」）：hook自動注入接力棒與身份。身份以實際環境（模型名稱、介面）為準；hook寫的跟實際不符時以實際為準，並修hook。回報不超過5行，不唸待辦。
- **收工**（教練說「總結」）：濃縮本場300~500字 → 更新接力棒 → 依N8判斷要不要寫記憶 → commit + push 給 hash。
- **接力棒**只留最新1~2棒＋三區待辦表（🙋要教練決定／🤫等教練自己提起／🔧AI自己的清單）；舊的搬進`handoff_archive/`（封存不是刪除）；教練裁示過的待辦當場移出。
- **犯錯當場**：寫進試金石案例庫 + commit。（原E05「更新top10_dynamic.md犯錯次數」刪除：08-31後就沒人照做）
撐住它的機制：`feed_junshi_handoff.sh`、`summary_upload_trigger.sh`、`handoff_sync_guard.sh`、`identity_model_verify.sh`

## 整體邏輯：三個結構問題

1. **同一條規則散在五個地方**：執行細則、全域CLAUDE.md鏡像、技能、hook、記憶檔各寫一次，改一處其他不會跟著改。建議分工：條文只寫在執行細則一次；技能與hook只寫「怎麼做」；記憶檔只放案例，不放規則。
2. **每次說話自動注入太多**：目前有14支程式在教練每次說話時都會跑（時間、守則提醒、執行合約、教練原話、專案卡……），規則彼此稀釋。今天的事就是證明：塞進來的具體清單永遠贏過抽象規則。這14支也該照同樣原則整併，這次先不動，等執行細則定案後一起處理。
3. **最常犯的錯要有條文對應**：9月前三名是查證不足、多此一舉的徵詢、輪詢設計，其中「輪詢」原本沒有條文，N5補上。

特助21守則是教練欽定的價值觀，本提案完全沒碰。
