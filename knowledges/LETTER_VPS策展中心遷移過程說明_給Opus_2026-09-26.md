## 一、起因：教練問了一個看似無關的問題，牽出整個架構

當天稍早，鑫瀚昌旅行社策展上架出了一個 bug（`custom_slug` 被系統的既有暫代頁覆蓋規則悄悄蓋掉）。我查出根因、修好、跟教練報告完，教練追問兩個問題：

1. 「我能不能直接叫赫米斯做，不用透過你？」
2. 「為什麼這件事會扯上 VPS？我們明明跟 VPS 一點關係都沒有。」

我查證（不是猜）發現：`shops.bymyway.com` 這個網域，實體真的架在 43.245.60.200 這台 VPS 上——跟「VPS 小龍蝦」（服務教練朋友的那台）**是同一台實體主機**。原因是這家店之前透過「加入我們」自助登錄表單註冊過，系統在 VPS 上建了暫代頁，後來策展上傳系統偵測到既有暫代頁就去更新那個頁面，而不是走 Mac 本機的 `/curated/` 路徑。

教練聽完之後，直接點出核心問題：**「當初用 VPS 是為了 24 小時不間斷接收新店家，但實際證明我們絕大多數不需要透過 VPS，直接在本地端就能解決。」**

## 二、教練給的決策框架（一字不改記錄，這是判斷力的來源）

教練沒有直接下令「拆掉」，而是給了三條判斷標準，要我自己評估：

1. 如果改起來很麻煩、變動很多 → 算了，不改
2. 如果不改也不會影響任何事情 → 不用改
3. 如果改了可以更好 → 改

並且補了一句原則性的話：「基於我們的信念，做對的事就要做；什麼叫對的事？就是長期有意義的事情就要做。」

這句話很重要——它給的不是「做這件事」的指令，是**判斷要不要做的方法**。我後面的評估過程，就是照這三條走。

## 三、我的評估過程（不是拍腦袋，是查證後才下判斷）

### 3.1 VPS 到底有沒有提供它原本要的好處？

查證發現：`event.bymyway.com`（策展上傳的入口本身、還有 `/curated/<slug>/` 的 GitHub 型網站）**本來就是跑在這台 Mac 上**，透過 Cloudflare Tunnel 對外（`~/.cloudflared/event-config.yml`，tunnel ID `739a34e4-9088-42f9-8819-ae1d2667e50e`）。

也就是說：如果 Mac 沒開機，整條「上傳店家網站」的流程本來就會停擺——VPS 有沒有 24 小時開機，並不會讓這個系統多任何一分可用性，因為上游（Flask app 本身）已經綁死在 Mac 上了。VPS 唯一多做的事，是幫「已經有暫代頁的店家」多存一份靜態檔案，並且多了一整條 SSH 管理邏輯（`sshpass`、遠端 mkdir/scp/tar）。

**結論**：VPS 沒有真的達成當初設想的「獨立於 Mac 之外的 24 小時可用性」。這是判斷「改了會更好」最關鍵的一步查證，不是猜的。

### 3.2 影響範圍有多大？

查 `_shops_slugs.json` 只有 3 筆記錄（huitou、kr、鑫瀚昌），實際 SSH 上去看 VPS 的 `/var/www/shops/` 目錄，發現：
- `kr`：已經是死的，目錄根本不存在（歷史殘留，跟這次遷移無關）
- `huitou`、`ema`（沒被記錄在 `_shops_slugs.json` 裡，是遺漏）、鑫瀚昌：3 家真實店家

**真實影響範圍很小**——這對應教練的第二條標準（不改也不影響什麼），反過來看：改動的成本也很小，因為只有 3 家真實資料要搬。

### 3.3 改起來麻煩不麻煩？

我查證這台 Mac 已經有現成的機制可以直接複用：
- Cloudflare API Token 已經存在（`路徑大全_憑證層.md`，範圍鎖定 bymyway.com 這個 zone），可以直接改 DNS，不需要教練手動去後台操作
- `/curated/<slug>/` 的服務邏輯（`_serve_repo_file()`）本來就是「serve 本機目錄」，我只需要多加兩條 Flask route，用 `request.host` 判斷是不是 `shops.bymyway.com`，直接複用同一套邏輯，不需要另外寫一個新的檔案服務系統

**結論**：三個條件都指向「該做」——不麻煩、影響小、做了明確更好。所以我直接動手做完，沒有停在評估階段回頭問教練。

## 四、實際執行的技術細節（給你接手時查程式碼用）

1. **下載 3 家店的內容**：`scp` 從 VPS 抓下來，發現 huitou/ema 其實早就有本機 git repo（比對 diff 只差 `.git` 資料夾，內容一致），只有鑫瀚昌是全新複製進 `/Users/bymyway/github_repos/hsinhan/`
2. **`event-signup/app.py` 新增兩條路由**：`shops_local_page()`/`shops_local_assets()`，用 `request.host.split(":")[0] != "shops.bymyway.com"` 擋掉非目標host，其餘邏輯直接呼叫既有的 `_serve_repo_file()`
3. **`_provision_shop_placeholder()`**（自助登錄表單那條路）：從 SSH mkdir+scp 改成本機 `mkdir`+`write_text`
4. **`scripts/curation_process.py` 的 `overwrite_shop_placeholder()`**：從 tar+scp+ssh 遠端解壓，改成 `shutil.rmtree`+`shutil.copytree`
5. **Cloudflare**：`~/.cloudflared/event-config.yml` 加一行 ingress（`shops.bymyway.com` 指向同一個 `localhost:5060`），DNS 從 `A` 記錄（指向VPS IP）改成 `CNAME`（指向跟 event.bymyway.com 同一個 tunnel）
6. **測試順序**：先用 `curl -H "Host: shops.bymyway.com" http://localhost:5060/...` 在本機直接測 Flask 路由邏輯，確認無誤後才動 DNS，DNS 生效後再用真實網域 curl 驗證，包含圖片資源的 Content-Type（不只看狀態碼）
7. **VPS 上的原始檔案完全沒刪**，留著當一段時間的備援

## 五、我自己捅出來又自己補上的 bug（誠實記錄，這才是完整過程）

執行完架構遷移後，我做了一次真實的端到端重傳測試（不是紙上談兵，是真的打 curl 到正式的上傳端點），結果發現：**我早幾個小時前為了修另一個 bug（custom_slug 被覆蓋）新增的 `rename_shop_slug()`，把 `_shops_slugs.json` 從「拼音key」改成「教練指定的短網址」之後，下次同一家店重新上傳，系統會用品牌名重新算一次拼音，卻已經找不到對應的舊 key，判斷成「全新店家」，重複建了一個 `hsinhan-2`**（包含重複的 GitHub repo、重複的策展中心卡片、重複的 registry 登記）。

我沒有隱瞞這個意外，而是：
1. 承認問題，追根究柢查出原因：`_shops_slugs.json` 舊格式是一份扁平清單，「品牌識別」跟「目前生效的網址」被綁在同一個值上，一旦網址被改名，識別能力就跟著死掉
2. 重新設計成 `{品牌拼音key: 目前生效slug}` 的字典格式，key 永遠不變、value 才能被改名機制更新
3. 清掉重複產出（本機目錄搬去 `.trash_2026-09-26/` 沒有直接刪、tainan-shangquan 重複卡片移除、registry 重複條目移除；唯一沒清掉的是 GitHub 上的 `hsinhan-2` repo，因為手上的 token 沒有 `delete_repo` 權限，已經沒有任何地方連過去，純粹是個孤兒但無害）
4. 重新測一次，確認不會再重複

**這一段的意義**：架構評估對了、方向對了，不代表執行細節不會出錯。真正的把關是「自己驗證到底、發現問題自己修，而不是宣布做完就走人」。
