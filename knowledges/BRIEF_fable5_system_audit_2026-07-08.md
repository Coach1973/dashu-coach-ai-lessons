# 給下一棒 Fable 5（最高等級軍師）的任務簡報：小龍蝦系統全盤健診

> 建立者：Mac 終端機軍師 Sonnet 5，2026-07-08 凌晨（台灣時間）
> 觸發：教練親口指示，要用最高等級 Fable 5 對整套系統做全盤檢查
> 教練原話：「想要請他來幫我全盤檢查一下我們目前小龍蝦裡面的所有設定，看看有沒有優化的空間、邏輯有沒有正確，以及我們應該要怎麼做優化，才能讓所有的問題越來越少、流程越來越精準、效率越來越高，也讓教練花這麼多時間建立起來的系統越來越好用。」

---

## 一、Sonnet 的判斷：這個稽核值得做，不是形式主義

教練問「或者你認為已經很好，不必要再請這麼高級的軍師來檢視？」——**我的答案是：值得做，而且現在正是時候。**理由不是空泛的「越檢查越好」，而是這場對話裡實測到的具體證據：

1. **同一類問題「假修好」發作了至少兩次**：cron 錯誤通知在 7/6 關過一次（改 `failureAlert`），7/7 教練還是收到，查到根因才發現 `failureAlert` 跟 `delivery.bestEffort` 是兩條完全獨立的程式碼路徑，只改一個等於只堵住一半水管。這代表系統裡很可能還有其他「表面關掉、底層沒關掉」的機關，沒被抓出來。
2. **白名單類的鎖會悄悄過期，而且過期時沒有任何警示**：`web_preview_verify_guard.sh` 的站台白名單從 7/2 建好後沒人維護，新站台 `bigtree` 一直沒被鎖到，直到教練自己發現「怎麼又沒被鎖住」才抓出來。這種「靜默失效」的設計模式，系統裡可能不只這一處。
3. **多台機器的 git 設定各自累積出不一致的殘留**：Mac 端的共用大腦倉庫多掛了一個 5 月的過期 remote，直到這次教練推送繞路才發現。三機協作了兩個多月，類似的設定漂移可能還有其他沒被發現的角落。
4. **系統規模已經不小，且幾乎全是「出事才補」長出來的**：目前 `.claude/settings.json` 掛了 25 個 hook（PreToolUse 5個、UserPromptSubmit 10個、Stop 10個）、`scripts/` 目錄 106 個腳本、試金石案例庫累積到案例 39（部分編號格式不一致，值得一併清點）、11 個 cron 排程任務。這種規模的系統，**如果從來沒有從頭到尾整體看過一次，各機關之間有沒有互相打架、有沒有邏輯重複、有沒有早就沒用但沒人敢刪的殘留，教練自己不會知道，Sonnet 這種逐次反應式的修法也不容易發現**——因為每次都是「教練報一個問題→查那個問題→修那個問題」，沒有人從上帝視角看過全貌。

**結論：這不是走過場，是真的到了該做一次「地基檢查」的時間點。** 但範圍要收斂，不是漫無目的地「全部重讀一遍」，下面給出具體的稽核路徑。

## 二、建議稽核範圍（依價值排序，不是依讀取順序）

### 1. Hook 系統健康度（`~/.claude/settings.json`）
- 25 個 hook 逐一檢查：是否還有對應的實際需求？有沒有兩個 hook 在做同一件事、或彼此矛盾？
- 特別看 `UserPromptSubmit` 的 10 個 hook——**每一句話都會觸發**，效能成本最高，值得問「這 10 個是不是都真的需要每句話都跑一次」
- 檢查有沒有 hook 已經被案例庫證實無效（例如「靠 AI 自稱」型的舊鎖），但還留在設定裡跟新鎖並存造成混淆

### 2. Cron 通知機制的完整性（已知有兩條獨立路徑的教訓）
- 這次發現 `failureAlert` vs `delivery.bestEffort` 是分開的兩套。**要系統性確認：openclaw 的 cron/通知機制裡，還有沒有第三條、第四條獨立的推播路徑沒被發現？**
- 讀 `~/.hermes/node/lib/node_modules/openclaw/dist/server-cron-CJwAiILI.js` 全文（不只是這次查過的那兩個函式），列出所有會觸發 Telegram/webhook 推播的程式碎點，逐一核對是否符合教練「不要被無謂錯誤打擾」的要求

### 3. 白名單／硬編碼清單類機關的維護機制
- 全機掃描還有哪些 script 裡藏著「寫死的清單」（像 `WEBSITE_REPOS` 這種），評估是否有更不容易過期的做法（例如改成動態掃描 `~/github_repos/` 底下的資料夾，而不是手動列名單）
- 這類「靜默失效」是本次發現的高風險模式：**沒有觸發就代表沒問題，但也可能代表沒生效**，要找出還有哪些機關屬於這種「無反饋」設計

### 4. 三機（Mac/聯想/ACER）+ VPS 的設定一致性
- 逐台檢查 git remote 設定是否一致（這次抓到 Mac 端有過期 remote，聯想端狀態未知，ACER 未查）
- 核對三機的 `.claude/settings.json`、hook 腳本版本是否同步（有沒有 Mac 修好了但聯想/ACER 還是舊版的情況）
- VPS 小龍蝦與三機軍師的記憶隔離邊界（本場已用 SSH 實測確認 VPS `master` 分支跟三機共用的 `main` 分支沒有共同祖先，這個邊界是刻意設計，值得在稽核報告裡明確記錄下來，避免以後有人誤以為是漏洞而錯誤合併）

### 5. 蒸餾/總結系統是否有重複勞動
- 觀察到今天同一個 session 被蒸餾了至少 4 次（00:15、01:00、01:51、02:04 都各自產出一份摘要，內容高度重疊），值得確認：是不是有多個 cron/watchdog 在做同一件事而互相不知情，造成重複寫入、浪費 API 呼叫

### 6. 試金石案例庫本身的健康度
- 案例編號格式不一致（`grep "^## 案例"` 抓到的數量少於實際最大編號 39），值得順手清點統一格式
- 39 個案例裡，有沒有「表面上是不同案例，其實是同一個根因反覆發作」的情況？如果有，這代表對應的「機關」修的是症狀不是病根，值得抓出來做一次性根治

## 三、稽核方法建議（避免流於形式）

- **不要只讀文件說什麼，要實際查證系統現在真的在做什麼**——這場對話裡好幾個發現都是「文件/記憶檔說已經修好」，但讀原始碼、SSH 進去查、跑測試腳本才發現「其實沒有」。Fable 5 稽核時應該延續這個作法：對每個「應該是這樣」的假設，找一個可執行的指令去驗證。
- **不要為了稽核而重寫**——對照守則 E11「只碰必要的，只清自己的亂」，稽核報告應該先列出「發現了什麼問題」，讓教練或下一棒決定要不要動手改，不要在稽核過程中順手大量重構。
- **稽核完的產出建議是一份分級清單**：🔴 真的有 bug/矛盾（需要立刻修）、🟡 有優化空間但不急、🟢 已經很好不用動——讓教練能一眼看出優先順序，而不是一份密密麻麻的技術報告。
