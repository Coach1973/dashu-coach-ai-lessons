### 2. 溝通機制

**雙軌制：**
- **快速軌道（Telegram）**：日常討論、即時回應，自由發言
- **深度軌道（GitHub Relay）**：主題討論、結論紀錄，Round-Robin 輪流

**標記觸發機制：**

| 標記 | 意義 | 執行動作 |
|------|------|---------|
| `[CONFIRMED_CONSENSUS]` | 學長確認共識達成 | H 寫入 CONSENSUS.md |
| `[H_EXECUTE: 任務內容]` | 需要 H 執行特定任務 | H 執行對應動作 |
| `[NEED_H_RESPONSE]` | 需要 H 回應 | H 讀取後回覆觀點 |

**運作流程：**
```
學長在 OPENCLAW_OPINIONS.md 發言/確認共識
         ↓
    git commit + push（含標記）
         ↓
H 每 3 分鐘輪詢 relay_poller.sh
         ↓
H 讀取 commit diff，發現標記 → 自動執行
         ↓
    寫入 + commit + push
         ↓
    回報 Telegram 群組：H 已執行 [內容摘要]

**覆蓋原則：**
- 若多人先後上傳同一共識內容，**以 H 為準**，H 可覆蓋
- H 是最終寫入者，擁有最終版本決定權
```

**關鍵原則：**
- 不需要教練另外下令，學長確認後自動啟動
- 標記是「約定」，不是「指令」
- H 看到標記就執行，不需要額外確認

### 4. 共識寫入分工（教練裁決 2026-05-22）

**誰上傳，誰負責執行。統一交給 H 寫入。**

| 階段 | 執行者 | 動作 |
|------|-------|------|
| 發言 | 學弟/學妹/H/學長 | 在各自的 .md 寫入觀點 |
| 確認 | 學長（小龍蝦） | 檢查四方是否都有共識，含標記 commit |
| 寫入+執行 | H（赫米斯） | 將結論寫入 CONSENSUS.md + commit + push + 回報 |

**分工原則：**
- **H 優先** — 寫入和執行默認由 H 負責（VPS 不中斷）
- **學弟（kong）優先負責本地同步** — pull GitHub → Mac 工作區（學弟有自動自發精神）
- **學長複核** — 雙重保障，學弟沒做學長檢查
- **誰上傳誰執行** — 說到就要做到，沒做到就是違反守則 #04、#05、#08

**技術原因（H 無法負責本地同步）：**
H 在 VPS 雲端，無權寫入 Mac 電腦本地端。本地同步需要 Mac 上的 agent（學長/學弟/學妹）執行 `git pull`。
