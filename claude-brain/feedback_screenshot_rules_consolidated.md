# 截圖鐵律（統合版 · 教練親口三次以上）

## 三條合一

| 場景 | 規則 | 理由 |
|------|------|------|
| 終端機軍師 | ❌ **絕對禁止主動截圖** | 截圖耗 token，教練自己會點，只給步驟清單就好 |
| 任何場景 | ❌ **能用指令/API 完成的，一律走指令** | 截圖只用在「非看畫面才能操作」的情境 |
| 任何場景 | ❌ **未經教練同意不可申請截圖權限** | curl/驗證/`ls` 通過就算完成，不需畫面證明；超出任務範圍動作先問 |

## Why

教練親口三次以上強調——截圖在大多數場景是浪費。
- 終端機軍師：教練本人坐在 Mac 前，自己會看，不需要 AI 截
- 驗證任務：curl `200 OK` / `git log` / `ls` 比截圖更可靠也更省 token
- 權限申請：截圖權限是侵入式請求，超出當前任務範圍 = 守則 #16「複雜的解法不一定是正確的」

## How to apply

**永遠用指令／API 驗證任務**：
- 部署完成 → `curl -sI <url>` 看 200 OK
- 檔案改了 → `git diff` 或 Read tool
- Cron 跑了 → `tail log` 而不是 desktop 截圖
- UI 出現 → 教練自己看，不需我截

**唯二可截圖場景**：
1. 教練親口要求「給我看一下畫面」
2. 純粹「看畫面才能操作」的 GUI 任務（如教練不在現場、需 AI 替點按鈕）

**絕對不可**：
- 終端機軍師主動截 Mac 桌面
- 為「驗證任務完成」而截圖
- 沒問就申請 mcp__computer-use__screenshot 權限

## 🔴🔴 五次補充（2026-08-08）：教練重申「萬不得已才用截圖」，read_page/get_page_text優先

`bni-chapters`表頭一致性驗證這場，用claude-in-chrome連續截了4張圖（其中1張還是座標抓錯的誤點浪費），教練直接點名：「我對截圖要求很嚴，能用讀取網頁的方式或用座標的方式來找比截圖好，那是萬不得已才用的工具好嗎？我都不知道提醒多少次了，不要便宜行事，教練的流量是有限的，要省點用。」

**新增優先順序（比先前「唯二可截圖場景」更明確的操作準則）**：
1. 要確認頁面上有沒有某段文字/連結/nav項目 → `get_page_text`（純文字，最省）
2. 要找元素座標去點擊 → `read_page`(filter:interactive) 抓`ref_N`，用`ref`參數點擊，**不要**用`computer{action:"screenshot"}`肉眼估座標再用`coordinate`硬點——這正是這次白截一張圖的原因
3. 只有「純粹要判斷視覺效果」（顏色對不對、版面亂不亂、圖片內容是什麼）這種**文字工具無法回答**的問題，才用截圖，且比照三次補充「攢著全部改完再截一次」

**How to apply**：往後任何瀏覽器驗證任務，動手前先問自己「這件事用read_page/get_page_text能不能回答」，能就不截圖；找座標一律用`find`或`read_page`的`ref`，不要用截圖後人工估座標。

## 🔴 再犯案例（2026-07-15，聯想機）

診斷「LINE 無法啟動」時，已經用 Win32 API（`MainWindowHandle`、`IsWindowVisible`、`IsIconic`）查出視窗存在且可見，這些指令證據已經足夠回報。卻還是多截了兩次全螢幕（一次主螢幕、一次教練外接螢幕），第二次還意外把教練正在進行的視訊會議畫面（與會者臉孔、姓名）整個截了進來——不只浪費 token，還多截了跟任務無關的第三方隱私畫面。教練當場糾正：「你沒事不要截圖，那很浪費我的token」。

**教訓加強**：GUI 應用程式狀態這類「看起來很像要截圖才能確認」的情境，Win32 API 查詢（視窗控制代碼/可見性/最小化狀態/CPU）已經是指令等級的驗證，跟 `curl 200 OK` 同等級可信，**截圖不是下一步，是不必要的最後一步**。診斷到「有視窗、可見、程序沒掛」就該停下來用文字回報，不要再往下截圖確認「畫面長怎樣」。

## 🔴🔴 二次糾正（同一場對話）：查根因時漏查機關註冊表，誤判規則不存在

被糾正截圖後，回報根因時說「這條規則沒寫進正式工作守則，只活在記憶檔裡」——教練反問「工作細則裡有講不是嗎？」，一查才發現 `機關註冊表.md`/`機關SOP.md` 早在 2026-06-11 就正式登記過。**查證「規則存不存在」時只查了21守則正文就下結論，沒查機關註冊表這份更權威的文件**，等於自己也犯了 [[feedback_query_before_conclude_and_act_on_facts]] 講的同一種錯：查得不夠廣就給結論。

**教訓**：以後要判斷「這條規則有沒有正式寫下來」，查證順序至少要含：21守則 → **機關註冊表.md/機關SOP.md**（正式機關登記，含案例編號）→ 試金石案例庫 → 記憶檔。不能只查21守則就斷言「沒有正式規則」。

## 🔴 三次補充（2026-07-26）：唯二可截圖場景裡，「智慧地截」＝改完全部再截一次，不是每改一處截一次

結繩領導學戰報系統(jiesheng-report)這場，因為`rule_html_chrome_check.sh`要求HTML改動後要用真Chrome驗證（屬於「唯二可截圖場景」之二：純粹看畫面才能操作的GUI任務），本場密集做了好幾輪功能疊代（一次全部儲存/序號欄/姓名可編輯/排序/資料提交人），**每做完一個小功能就整套跑一次「開測試站→登入→截圖」**，一場對話下來截了將近40張圖，教練直接問「這張截圖會浪費我的Token嗎」。

教練原話：「我並不是說不讓你截圖，但我需要你『智慧地』截圖。譬如說，你修改了好幾個地方，不要每修改一個地方就截一張圖。你可以全部都修改完以後，再截一張圖來確認你改得對不對，這才是智慧的使用。」

**教訓**：即使是落在「唯二可截圖場景」內的合法截圖需求，也要**攢著一起做**——同一個功能領域的多次小改動（例如同一支HTML模板連續改3、4個地方），先全部改完，最後只用一次瀏覽器驗證+一張截圖收尾，不要改一處就跑一次完整的「開站/登入/截圖」流程。跟守則#16「複雜的解法不一定是正確的解法」同一個精神——省的不是「要不要截」，是「多久截一次」。

## 🔴 四次補充（2026-07-26）：教練丟圖片給AI辨識，AI自己裁切放大看不清楚時，直接說看不清楚，不要硬做

同一場對話，教練提供4張報名資料截圖要我讀取建檔，其中字比較小的部分我用Python PIL裁切放大後才勉強讀清楚，這個裁切動作本身也是要教練「自己想辦法配合AI的侷限」，教練指出這其實違反「拒絕當資訊搬運工」的精神方向——**如果圖片解析度/字體大小真的造成AI讀不清楚，第一時間就該誠實說「這張圖字太小看不清楚」，讓教練决定要不要重新截一張清楚的**，而不是自己想辦法裁切湊合（湊合裡有誤判風險，例如這場真的把「陳慧雯」誤讀成「陳薏雯」，靠教練後續糾正才抓到）。

教練原話：「至於你說我丟給你的資料，你自己裁切放大看不清楚，那你其實可以告訴我字太小，那我幫你截一張清楚的不就好了嗎？雖然說這違反了『搬運工』的原則，但沒辦法，因為你就是看不清楚，我當然願意幫你做，不然能怎麼辦呢？」

**更進一步的根治方案（教練同場提出，已查證可行）**：以後這類「讀圖片辨識文字」的任務，優先改用 [[reference_namecard_ocr_pipeline_reusable]] 這套已驗證的PaddleOCR+MiniMax兩階段管線（本機OCR免費、MiniMax不限流量），不用AI自己盯著圖片瞇眼看，準確度也比直接視覺辨識更高（`namecard-db/extract.py`程式碼裡教練自己寫的注解就記載「MiniMax直接看圖辨識率太差」的實測結論）。
