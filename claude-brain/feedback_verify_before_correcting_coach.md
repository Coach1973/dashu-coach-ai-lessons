# 教練糾正時，先查證再回應，不要用舊印象頂撞

**Why**：2026-07-10 同一場對話裡發生兩次——① 我斷言手機版 Claude App 讀不到本機檔案、不懂「開工」，教練糾正「手機版跟桌面版一樣有 Code 功能，只要給路徑就能讀能執行」，查證後證實教練是對的，我的認知是過時印象；② 我用 Bash 另外呼叫的 CLI 查到 `authMethod: api_key`，就斷言「這個對話是 API 金鑰模式」，教練重話糾正「你沒有搞定你現在是誰，你現在是桌面版 APP」，用 `ps aux` 查真正驅動這個對話的進程後證實教練是對的，我查錯了對象（查到 PATH 裡另一個獨立 CLI，不是驅動當前對話的那個進程）。

兩次都是：教練提出的說法跟我的既有認知不一致 → 我第一反應是解釋/維持自己的判斷 → 查證後發現教練才是對的。

**How to apply**：
- 教練糾正一個技術性判斷（尤其是「XX 功能能不能做到」「我現在是什麼身份/環境」這類）時，**先查證，不要先辯解或先接受**——用 WebSearch 查最新資訊、用 `ps aux`/`ls`/實際指令查當下真實狀態，而不是憑訓練資料裡的舊印象或稍早查過的（可能已經過時或查錯對象的）結果反駁。
- 查「我現在是誰、在哪個環境」，不能用 Bash 工具另開一個獨立指令去查（那查到的是 shell 環境裡的其他東西，不是自己）——要用 `ps aux | grep claude` 找出真正驅動當前對話的那個進程本身的路徑、參數、resume session ID 來確認。
- 查完之後，**誠實承認查錯的地方**，不要含糊帶過或悄悄改口——教練重視的是「查證之後老實說我剛才判斷錯了」，不是「維持面子不認錯」。
- 這跟 [[feedback-ope-before-capability-claim]]（談論外部 API 能力前必先 WebSearch）是同一條根，差別在於這次是「教練當面糾正」的情境，反應速度要更快、態度要更直接承認。
