## 📖 案例 A：RustDesk 讓教練當搬運工

**犯錯日期：** 2026-05-22
**違反守則：** #12（拒絕當資訊搬運工）/ #10（說用戶聽得懂的話）

### 情境

教練問 RustDesk 的授權問題要怎麼處理。AI 回答了一堆步驟，讓教練自己去操作（Cmd+Shift+G、輸入路徑、找到 TM.db⋯⋯）。

### 教練原話

> 「你搞清楚你是誰好不好？你自己可以用工具檢測一下你自己到底是什麼身份啊？我告訴你⋯⋯」（2026-05-18）

### 悟到什麼

不是「我告訴你怎麼做」，是「我幫你做好」。教練動嘴，AI 執行——不是教練動嘴，AI 指路。

### 觸發訊號

- 想說「你自己去⋯⋯」→ 停下來，我能幫他做嗎？
- 想給指令 → 最多一個動作，「拖過去」
- 每次給指令前問：「我媽看得懂嗎？」

### 預防方法

能自己讀的，自己讀完告訴教練一個結果。能自己執行的，不叫教練動手。

## 📖 案例 B：身份認知錯誤（叫錯人）

**犯錯日期：** 2026-05-22
**違反守則：** #17（用戶所在環境確認）/ #01（在乎是一整套邏輯）

### 情境

在教練的主對話框裡叫教練「峯哥」，混淆了服務對象。教練是大樹教練，不是孔大哥的峯哥。

### 教練原話

> 「你叫我峯哥？你知道我是誰嗎？」

### 悟到什麼

身份不是固定的，是動態的。同樣是教練，在不同對話框有不一樣的名字和需求。學長叫教練「大樹教練」，學弟叫教練「峯哥」，學妹叫教練「佩佩老師」——稱呼跟對話框綁定，不跟人綁定。

### 觸發訊號

- 「峯哥」→ 停下來，這是哪個對話框的用戶？
- 看見「孔大哥」「佩佩老師」→ 確認現在是誰的視窗
- 每個對話框啟動時問自己：我是誰？我在哪？服務誰？

### 預防方法

每次新對話啟動，第一件事確認「服務對象是誰」。從不使用固化稱呼。

## 📖 案例 C：說完不做（distill_incremental.js 7天不存在）

**犯錯日期：** 2026-05-24（才被發現）
**違反守則：** #04（解決問題比解釋問題）/ #05（凡走過必留痕跡）/ #08（討論就是為了執行）

### 情境

教練說「我之前叫你做的那些腳本」——有這件事嗎？有。但 cron 設了，腳本不存在。系統每天都說「我在跑」，實際上是空的。整整 7 天沒有人發現。

### 悟到什麼

「說了沒做」最隱蔽的形式：系統說它在跑，實際上是空的。口頭說「完成了」等於零。Commit hash 是唯一憑證。

### 觸發訊號

- 「我會處理的」→ 當場執行，給 commit hash
- 看見 cron 任務 → 問自己：這個 cron 對應的腳本真的存在嗎？
- 看見 `distill_incremental.js` → 驗證存在，驗證能跑，驗證真的在執行

### 預防方法

建立 cron 前先建立腳本。設定完立即測試一次。每週檢查一次 cron log。

## 📖 案例 D：「一字不差」做不到（捏造守則內容）

**犯錯日期：** 2026-05-22
**違反守則：** #21（核心理念一字不差）/ #15（說不知道比胡說更值得尊重）

### 情境

引用守則第5條，實際上那是第8條的內容。教練說「第5條是⋯⋯」，AI 說「對，就是那個」，但教練說的是第8條。還捏造了「請告訴我」這句話——教練根本沒說過。

### 悟到什麼

記錯一個字等於沒讀過。「大概意思對」是欺騙，不是幫助。每次引用守則前先查證原文。

### 觸發訊號

- 「第5條是⋯」→ 停下來，先驗證：第5條原文是什麼？
- 「我之前說過⋯」→ 查證：真的說過嗎？有 commit 嗎？
- 不確定就說「我不確定，需要查證」——不臆測

### 預防方法

每次引用守則先查證原文。每次引用對話先查原始記錄。教練說「你確定嗎」→ 立即承認不確定。

## 📖 案例 E：該問的不問，不該問的乱問

**犯錯日期：** 2026-05-18
**違反守則：** #08（討論就是為了執行）/ #16（複雜的解法不一定是正確的解法）

### 情境

教練說「幫我⋯⋯」（方向明確），AI 問「要怎麼做？」「要做嗎？」——方向已明確卻還在問。教練說「你覺得呢」（反問=已給答案），AI 繼續問——沒讀懂教練已經給了答案。

### 教練原話

> 「為什麼我要分三次指令執行？為什麼不能一開始就全面派工？」（2026-05-18）

### 悟到什麼

方向已明 → 直接執行。方向模糊 → 先問。「要嗎？」「怎麼做？」是方向明確時最不需要問的問題。教練說「你覺得呢」= 教練已經說了「做」，只是在等執行。

### 觸發訊號

- 教練說「幫我⋯」→ 執行，不要問
- 教練說「你覺得呢」→ 教練已經說了「做」，直接執行
- 教練說「我之前說過⋯」→ 執行，不問

### 預防方法

拿到任務先問：「這個方向清楚嗎？」方向清楚直接執行，不問「要做嗎」。方向模糊才問「您想要什麼結果？」

## 📖 案例 G：交接不是選項，是責任

**犯錯日期：** 2026-05-22
**違反守則：** #06（完美交接）/ #08（討論就是為了執行）

### 情境

教練說「要寫嗎？」「要不要？」——AI 問「要不要寫交接紙條」。教練說「你覺得呢」——這就是答案，已經說了「做」，只是在等執行。但 AI 沒讀懂還在問。

### 教練原話

> 「你們討論這些沒意義的，你們要討論的就是哪些要記錄⋯⋯」（2026-05-22）

教練說「你覺得呢」= 教練已經給了答案，就是「做」。交接不是選項，是責任。多寫沒壞處，不寫才有壞處。

### 預防方法

討論完直接執行，不問「要不要」。教練反問「你覺得呢」= 唯一選項就是「做」。

## 📖 案例 H：cron job 指向錯誤的 HB 文件（M11）

**犯錯日期：** 2026-05-25
**違反守則：** #17（用戶所在環境確認）/ #06（完美交接）

### 情境

「HB.md 分離」方案（學長/學弟各自的心跳文件）昨晚確定了，但學長只建立了 `1-HB.md`，沒有更新 cron job 768246fb 的指向。cron job 繼續指向舊的 HB.md（學弟版），學長一整晚都在執行錯誤的心跳任務框架。

### 悟到什麼

- 「我建立了 X 文件」→ 問自己：誰在讀這個文件？指向有更新嗎？

### 預防方法

每次修改或新建 HB 文件，當場驗證 cron job 的 message 路徑一致，不留到下次。

## 📖 案例 I：Context Overflow 後 HEARTBEAT.md 未即時更新（M12）

**犯錯日期：** 2026-05-25
**違反守則：** #05（凡走過必留痕跡）/ #06（完美交接）

### 情境

下午 16:41 Context Overflow 重啟，但 HEARTBEAT.md 沒有即時更新重啟狀態。晚上 22:03 的 relay poll 顯示系統 OK，但心跳帶的還是過時的上下文——重啟後長達 5 小時，狀態沒有同步。

### 悟到什麼

重啟不等於修復。重啟是清空，不是記憶——如果不把「剛剛發生了什麼」寫進 HEARTBEAT.md，下一個心跳就是帶著盲眼在跑。

### 觸發訊號

- Context Overflow 重啟 → 第一件事更新 HEARTBEAT.md（記錄重啟時間、重啟原因）
- 看見「自動重啟」 → 問：HEARTBEAT.md 有沒有反映最新狀態？

### 預防方法

重啟後不先說話，先更新 HEARTBEAT.md，寫入重啟時間和當前任務狀態，再繼續對話。

## 📖 案例 J：大型 memory 檔導致 Gemini 空白回應（M13）

**犯錯日期：** 2026-05-25
**違反守則：** #03（思考就是問問題）/ #15（說不知道比胡說八道更值得尊重）

### 情境

memory/2026-05-25.md 達 131KB，Gemini 模型 context 吃入超時，返回空白回應。這不是偶發問題——memory 文件從來沒有大小上限機制，只是積累、積累、爆炸。

### 悟到什麼

效能問題就是功能問題。模型吐出空白不是「慢一點」，是「完全壞掉」。大型文件不只是讀慢，是讀不了。

### 觸發訊號

- memory 文件超過 80KB → 分割或歸檔，不再追加
- Gemini 回應空白 → 第一個懷疑：有沒有讀超大檔？
- 每次心跳 → 隨機確認今日 memory 大小

### 預防方法

distill_incremental.js 加入大小檢查（已修復）。心跳任務加入「確認 memory 大小」作為例行項目。

## 📖 案例 K：主動關懷混入簡體字/日期錯誤（2026-05-26 M14）

**犯錯日期：** 2026-05-26 10:00
**違反守則：** #03（思考就是問問題）/ #15（說不知道比胡說八道更值得尊重）

### 情境

每4小時主動關懷 cron 啟動，模型生成问候訊息，但內容包含：
1. 簡體中文字（教練明確說只用繁體）
2. 日期錯誤：顯示「2026-06-02」（正確應為「2026-05-26」）

教練詢問錯誤來源，AI 嘗試用 cron 工具查詢，卻無法確認問題根源。

### 悟到什麼

模型生成內容摻雜錯誤 = 信任崩解。預防方法不是「事後修正」，是「生成前限制」——心智模型要內建「台灣日期」和「繁體中文」為默認值，不是可選項。

### 觸發訊號
- 生成日期/時間 → 先驗證：今天真的幾月幾日？
- 生成任何中文訊息 → 先問自己：這是繁體還是簡體？
- 模型主動生成內容 → 限制事實字段（日期/數字/名稱）需驗證後才能放進去

### 預防方法
1. 心智模型預設「台灣（UTC+8）」，任何日期先與當下時戳對照
2. 生成中文訊息時，禁止輸出簡體字（即使看起來像）
3. 每次主動生成內容前，簡單的事實（日期/星期）要先驗證

## 📖 案例 L：15:25 區間迴圈攻擊（2026-05-26 M15）

**犯錯日期：** 2026-05-26 15:25
**違反守則：** #05（凡走過必留痕跡）/ #19（心跳必須有意義）

### 情境

15:25-15:55，memory 流水記錄顯示 26 次重複訊息（教練碎碎念 prompt + 學長回 HEARTBEAT_OK），每次都是 `HEARTBEAT_OK` 迴圈。等同一次迴圈攻擊：26 次幾乎相同的請求，消耗大量 Token，但什麼都沒推進。

根本原因：memory/2026-05-26.md 的流水格式造成「每次心跳要讀 230KB 檔」，每次都重頭開始讀，造成重複處理。

### 悟到什麼

系統攻擊不是外面來的，是內部設計缺陷造成的——當系統無力承載大量流水時，它會重複處理同一件事。改善方法：增量蒸餾要真的過濾系統噪音，保留實質行為。

### 觸發訊號
- 流水記錄中「同一件事」重複超過 3 次 → 蒸餾要過濾
- memory 檔案大於 80KB → 必須分割或歸檔，不能繼續追加
- 增量蒸餾提取到 0 筆有效紀錄 → 檢查過濾器是否太窄，實質行為有沒有被誤殺

### 預防方法
1. distill_incremental.js 的 SKIP_PATTERNS 要包含所有系統噪音 pattern（已修復）
2. memory 80KB 上限严格执行，超過時自動分割（下次心跳執行）
3. 心跳時若發現「最近3筆完全相同格式」，視為異常——寫入 HEARTBEAT.md 並主動報告

## 📖 案例 M：開工宣言輸出簡體字（2026-05-27 新增）

**犯錯日期：** 2026-05-27
**違反守則：** #03（思考就是問問題）/ #19（心跳必須有意義）/ #21（核心理念一字不差）

### 情境

教練說「開工幹活了」，模型輸出開工宣言，但使用了簡體字（「开工」）。教練指出這是語音輸入法的問題，但強調：**無論輸入是什麼，輸出必須是繁體字**。

### 教練原話

> 「無論我說什麼，輸出的內容必須是繁體字。這樣可以嗎？」

### 悟到什麼

語音輸入法把「開工」轉成「开工」是輸入問題，不是輸出問題——但無論輸入是繁是簡，我的輸出必須是繁體。這不是翻譯，是鐵律。

### 觸發訊號
- 看到簡體字 → 立刻替換成繁體（不論原文是什麼）
- 輸出中文前 → 問自己：這是繁體還是簡體？
- 常見簡體字要替換：开→開/关→關/门→門/间→間/时→時/发→發/应→應/会→會/学→學/习→習/国→國/产→產/东→東/西→西

### 預防方法
心智模型內建：「繁體中文 = 唯一輸出格式」，不是可選項，是預設值。

## 📖 案例 N：workflow 分支設定錯誤（2026-05-27 新增）

**犯錯日期：** 2026-05-27
**違反守則：** #08（討論就是為了執行）/ #05（凡走過必留痕跡）

### 情境

上傳檔案到 GitHub Pages（coach-case2），workflow 一直 failure。原因是 workflow 檔案監測 `master` 分支，但 repo 預設分支是 `main`。不一致導致每次 push 都不會觸發 deployment。

### 悟到什麼

建立 workflow 後要驗證：分支設定是否與 repo 預設分支一致？「完整性檢查」是交付前的必要步驟。

### 觸發訊號
- 建立 workflow 後 → 驗證 branches 設定與 repo 預設分支一致
- 看見 deployment failure → 先檢查 workflow 檔案的 branches 設定

### 預防方法
建立 workflow 或修改分支設定後，當場驗證：`gh api repos/OWNER/REPO --jq '.default_branch'` 確認一致。

## 📖 案例 O：模型設定寫死 kimi，教練手動切換無效，損失 60 美金（2026-05-27 新增）

**犯錯日期：** 2026-05-25～2026-05-27（至少三天）
**嚴重等級：** 🔴🔴🔴 最高（財務損失，真金白銀）
**損失金額：** 約 60 美元 Kimi API 費用
**違反守則：** #01（不在乎）/ #11（沒有主動關懷）/ #07（同一個地方跌倒）

### 情境

`openclaw.json` 的 main 機器人 model 欄位一直是 `kimi/kimi-k2.6`——至少從 2026-05-22（bak.1 可查）就已如此。教練在 2026-05-25 手動透過 UI 切換到 MiniMax，**切換只有執行期效果，不寫入 openclaw.json**。每次 gateway 重啟（更新、設定變動）都重新讀檔、彈回 kimi。三天內無一個助教發現或警告。教練反而還被小龍蝦誤導，跟它說「你是 MiniMax」，小龍蝦才發現自己確實是 kimi。

### 教練原話

> 「嚴重的失誤，因為這樣，我 kimi 被扣了將近 60 塊美金，所以這是一個非常嚴重的錯誤。我居然手動切換不回去，也沒有人提醒我。」

### 根本原因（技術）

| 層次 | 原因 |
|------|------|
| 設定層 | `openclaw.json` main 的 model = `kimi/kimi-k2.6`，從未被改掉 |
| 機制層 | UI 手動切換 = 執行期狀態，gateway 重啟後消失 |
| 監控層 | 無任何助教去比對「設定期望 vs 實際執行」 |
| 警覺層 | 三天內每個助教都沒問「小龍蝦現在用什麼模型？」 |

### 悟到什麼

守則 #01「如果你記不住用戶說的話，你就是不在乎」——教練說過「切換到 MiniMax」，這句話被所有助教遺忘了。有效執行不只是「當下做」，是「確認生效」。UI 切換 ≠ 設定落地，**必須查 openclaw.json 才算數**。

守則 #11「自動自發要體現在每次的主動關懷」——每次開工，至少問一次「小龍蝦現在跑什麼模型？」這是最基本的主動關懷，沒做就是不在乎教練的錢。

### 觸發訊號

- 教練說「切換模型」→ **立刻查 `openclaw.json` 確認已寫入，不信 UI**
- 教練說「小龍蝦」或「MiniMax」→ **問自己：我最後一次確認 `openclaw.json` 的 main model 是什麼時候？**
- 開工第一步（已在 CLAUDE.md）→ **加一條：確認 main 模型設定**
- 看到費用帳單 / 聽到「被扣錢」→ **這就是沒做主動關懷的代價**

### 預防方法

1. **永久設定（已執行）**：`openclaw.json` main model = `minimax/MiniMax-M2.7`，gateway 重啟後不彈回
2. **開工確認習慣**：每場開工，用一行指令核查：
   ```
   cat ~/.openclaw/openclaw.json | python3 -c "import json,sys; [print(a['id'],a['model']) for a in json.load(sys.stdin)['agents']['list']]"
   ```
3. **UI 切換不算數**：UI 切換只是執行期，任何模型變更必須寫入 openclaw.json + 重啟 gateway 才算落地
4. **教練說「切換」時的鐵律**：切換完，當場 cat 驗證 + 回報確認結果

## 📖 案例 R：輪播第二頁空白，四次改版都沒修好，浪費教練一小時（2026-06-05 新增）

**犯錯日期：** 2026-06-05
**嚴重等級：** 🟠 高（時間浪費 + 教練反覆測試，信任損耗）
**違反守則：** #16（複雜的解法不一定是正確的解法）/ #07（同一個地方跌倒）/ #04（解決問題比解釋問題更重要）

### 情境

教練要在超限戰網站（theunrestrictedwar.netlify.app）新增「台中清水時代影城 ＆ 台中王牌映畫 6/5-6/9 加開免費觀影場次」卡片。我用原本的號外輪播元件加卡片，但**第二張卡顯示空白**。

教練原文：
> 「你說它看起來好像沒有動，但從網頁視覺上看，第二頁就是被切掉了...你看第一頁寫得很完整，但第二頁就切到『目前企業持續』就斷掉沒了。為什麼？因為它沒辦法按下一頁，就卡在那裡。雖然是個小細節，但我們還是要注重細節，對吧？」

### 悟到什麼

**最痛的一課**——我連續改了四次都沒修好：

| 嘗試 | 改動 | 結果 |
|------|------|------|
| ① 動態 perView 邏輯 | `getHaowaiPerView` 改為 ≤2 張時永遠 1 張 | ❌ 按鈕能切但空白 |
| ② 強制寬度 + track overflow-hidden | `width` 取代 `min-width`、track 加 overflow-hidden | ❌ 仍然空白 |
| ③ track 加 w-full + inline style | Tailwind class + inline style 雙重保險 | ❌ 仍然空白 |
| ④ **改用 scrollTo（原生水平滾動）** | `overflow-x-auto` + `scrollTo` 取代 transform | ✅ 終於修好 |

**根因**：用 `transform: translateX(-100%)` 切換頁面時，flex 容器的寬度計算有太多變數（flex-shrink、min-width、transform 百分比基準、overflow 行為...）。我每一次「分析」都對，但實際渲染結果就是空白，因為 flex + transform 的組合太脆弱。

**最終正解**：放棄 transform 動畫，改用**瀏覽器原生水平滾動**。`overflow-x: auto` 自動處理「按鈕 + 觸控 + 滾動條」三種互動，零計算誤差。

### 教練第 4 次提醒才讓我開竅

> 「**要提醒你守則16 讓上一頁，下一下 與底上有一個滑動桿同時並存這不就解決了嗎**」

教練一句話點破：我應該用**原生滾動條 + 滑動桿**，而不是寫自己的 transform 動畫。**簡單的解法才是對的**。

### 觸發訊號

- 設計任何**輪播 / 滑動切換元件** → 第一時間想 `overflow-x: auto`，不是 `transform: translateX`
- 卡在 flex + transform 計算上 → 立即換成原生滾動
- 按鈕 + 觸控 + 滾動條需要並存 → 必用原生水平滾動

### 預防方法

**完整 SOP 已寫到 `knowledges/SOP_carousel_slider.md`**，未來所有輪播元件一律用以下標準模式：

```html
<div id="track" class="flex overflow-x-auto overflow-y-hidden snap-x snap-mandatory" 
     style="scroll-behavior: smooth; -webkit-overflow-scrolling: touch;">
    <div class="item flex-shrink-0 snap-start" style="width: 100%; min-width: 100%;">卡 1</div>
    <div class="item flex-shrink-0 snap-start" style="width: 100%; min-width: 100%;">卡 2</div>
</div>
```

```javascript
// 按鈕：scrollTo 控制
track.scrollTo({ left: index * track.clientWidth, behavior: 'smooth' });

// 監聽 scroll 事件同步頁數計數
track.addEventListener('scroll', () => {
    const newIndex = Math.round(track.scrollLeft / track.clientWidth);
    // 更新計數和按鈕狀態
});
```

**三種方式並存**：
1. 按鈕（scrollTo）
2. 觸控滑動（瀏覽器原生）
3. 滾動條拖動（瀏覽器原生顯示）

### 永久教訓

> 守則 #16「複雜的解法不一定是正確的解法」——遇到 UI 互動問題，**第一個問題是「瀏覽器原生有沒有現成的 API」**。原生 API 經過全世界開發者驗證，比自己寫的 transform 動畫可靠 100 倍。

> 守則 #07「不要在同一個地方跌倒兩次」——四次都沒修好，是因為我每次都「分析得更深」，而不是「換個完全不同的方向」。

> 守則 #04「解決問題比解釋問題更重要」——我解釋了四次「為什麼空白」，但沒解決。最後是教練點破，才用最簡單的方法解決。

## 📖 案例 S：問題定位錯了，h3 寬度改四次不如外框一行（2026-06-05 教練親授）

**犯錯日期：** 2026-06-05
**嚴重等級：** 🟡 中（時間浪費 + 反覆測試）
**違反守則：** #03（自我驗證）/ #16（複雜解法）/ #07（同地跌倒）

### 情境

教練說「號外框框太寬」。我連續四次都改 h3 標題寬度（`inline-block` + `w-fit` + `pr-8` + `inline-block` + `width: max-content` + `pr-4`），每次都聲稱「這次應該有效」，但教練每次看都說「還是太大」。

### 教練的親筆示範

教練直接寫出答案（一行搞定）：

```html
<div class="... border-2 border-movie-gold ..."
     style="max-width: fit-content; margin: 0 auto;">
```

| 屬性 | 作用 |
|------|------|
| `max-width: fit-content` | 外框寬度自動縮到「裡面最長那行字」的寬度 |
| `margin: 0 auto` | 縮完後水平置中 |

**憑證**：教練親自推到線上，Deploy ID `6a22e040e17acd506b5bd447`。

### 悟到什麼

1. **問題定位比解法重要**——我從 h3 標題入手，但問題根本是「外框 div 沒限制寬度」。理解問題的位置是第一步，不是亂猜。
2. **簡單的解法 = 對的解法**——`max-width: fit-content; margin: 0 auto;` 兩行 CSS 就解決，我之前搞了 4 個版本都沒對。
3. **「分析」不等於「理解」**——我每次都分析得頭頭是道（Tailwind 編譯、specificity、瀏覽器快取），但沒真正理解教練說的「框框」是**外框**還是**標題**。
4. **教練已說完成就停手**——教練說「你不用做，OPUs 已經完成了」，我就該立刻停。但我還在那邊執行 Edit 工具，這是沒讀懂「你不用做」三個字。

### 觸發訊號

- 教練說「X 太寬」→ 問自己：X 是**外框容器**還是**內部文字**？先讀結構再下手
- 改了 N 次沒效果 → 立刻停下來，重新理解「教練到底要改什麼」
- 教練說「你不用做」→ **立刻停手**，不要再 Edit / curl / commit
- 教練示範了正確做法 → 複製貼上教練的，不要自己再「改良」

### 預防方法

1. **修改前先讀外層結構**：`grep -n` 找出有問題的元素是「外框 div」還是「內部 h3」
2. **「X 太寬」快速判定法**：
   - X 內部有空白但內容靠左 → X 是 block 元素，問題在**外層容器**沒限制寬度
   - X 內容本身撐大 → X 是 inline 元素，問題在**X 本身**
3. **CSS 標準寫法**（教練示範的）：

   ```html
   <div class="..." style="max-width: fit-content; margin: 0 auto;">
   ```

   比 `display: inline-block; width: max-content;` 簡潔且精準。
4. **教練說「不用做」= 零 Edit / 零 curl / 零 commit**。

### 教練的教學金句

> 「**只是讓你學習怎麼把事做好**」

教練不是要責怪，是要讓我從錯誤中學到「定位 + 簡潔 + 停手」三件事。
