## 🔴 模式 #1：輪詢（定時檢查）取代事件觸發 —— 累計 6+ 次，最高頻

**核心教訓**：遇到「沒有現成事件掛鉤」的情境，第一反應永遠是「那就設一個時間間隔去檢查」，而不是先窮盡「有沒有辦法讓事情發生的當下直接觸發」。**拉長輪詢間隔（例如30分鐘→改成2小時）不是修法，是同一個錯誤的兩個答案**——教練要的是「沒事發生就完全不查」，不是「查得比較不頻繁」。

**涉及案例**：案例32（心跳定時打卡）、案例36（陌生用戶開通輪詢，教練第3次糾正）、案例49（Amber名片資料夾輪詢，教練第4次糾正）、`feedback_event_driven_not_polling_pattern.md` 記錄的第5、6次發作（RustDesk記憶體監控、Stop hook regex繞過）。

**自動化防護狀態**：⚠️ 部分——`stop_rules_master.py` 規則D 會攔「每N分鐘/每N小時檢查」這類措辭，但案例66證實這支機關本身曾瞎眼35天（見模式#2），且regex覆蓋面不夠、同義改寫可繞過（掃/查/讀取/巡邏/處理等動詞尚未全部涵蓋）。

**觸發詞**：心裡浮現「要多久檢查一次」「間隔設短一點還是長一點」「這樣會不會太頻繁」→ 立刻停下反問：這件事發生的當下，有沒有辦法讓當事人或系統直接觸發？教練問「這樣會不會很耗資源」→ 這不是要你調整數字，是在提示整個機制方向錯了。

**最近一次**：2026-08-27（案例66，攔截這個模式的機關本身失效）

## 🔴 模式 #2：機制/hook「看起來存在、程式邏輯看起來對」，實際上早已失效沒人發現

**核心教訓**：建立防呆機關、監控腳本、cron 排程，如果沒有用**真實資料**驗證過完整跑一輪，很容易在某個環境變化後悄悄失效，卻因為「表面上看代碼邏輯是通的」而沒人發現，直到教練自己撞見才揭穿。

**涉及案例**：案例40（cloudflared差點被當可疑程式關掉）、案例45（context 80%預警規則形同虛設，fire-and-forget bug）、案例52（三機每日總結誤報「連續11天沒對話」，判斷邏輯依賴從未真正運作的中繼檔案）、案例53（HEARTBEAT誤報Telegram失效133小時，盲信衍生旗標第3犯）、案例56（LINE群組長期失效，`accounts.default`設定被外掛原始碼結構性忽略）、案例64（聯想「總結」收工hook缺jq指令靜默失效近一個月）、案例66（守則#07輪詢偵測機關瞎眼35天，把工具回音誤判成回合邊界）。

**自動化防護狀態**：❌ 這個模式本質上是「防呆機關本身需要被驗證」，很難再套一層機關去驗證機關——目前唯一解法是**紀律**：任何新建的 hook/cron/監控，建立當下必須用**真實資料重播**（不是合成的單輪測試）驗證過一次，且要定期（例如每次改動相關程式碼時）重新驗證，不能只信「代碼邏輯看起來對」。

**觸發詞**：要新建或修改任何 hook/監控/cron → 建完當下必須實跑一次驗證，且用真實歷史資料而非憑空編造的測試案例；教練說「連續N天沒有」「一直沒有」「好像斷了」「查無紀錄」→ 先查真相源，不要信中繼/衍生資料。

**最近一次**：2026-08-27（案例66）

## 🔴 模式 #3：查證優先於試錯——遇到卡住先查證根因，不要靠 UI/操作試錯繞圈

**核心教訓**：遇到「設定看起來對、但就是不生效」的問題，第一直覺常常是靠試錯（換個地方點點看、加個選項試試看），而不是先做 WebSearch 查官方文件、或去看系統自己的狀態頁/log。試錯的隱藏成本（時間、token、教練的耐心）遠高於一次精準的查證。

**涉及案例**：案例42（禁止問教練「記不記得」，建立七層查證系統）、案例51（Zoom E碟增量資料查證方法有漏洞，錯誤回報導致教練誤判要刪正牌資料）、案例55（沒查路徑大全就回報「VPS查不到」）、案例57（看到陌生provider name就瞎猜對應服務）、案例59（`find -maxdepth`深度算錯，誤判「早已存在的檔案」不存在）、案例61（ezPay查「無Email」直接下結論，沒交叉比對同音字/姓名顛倒）、案例67（FB API卡權限，繞一大圈UI試錯才發現真因是商家驗證未完成）。

**自動化防護狀態**：❌ 純紀律層面，無法自動攔截——這是判斷力問題，只能靠每次卡住時主動問自己「我試錯超過幾輪了？該停下來查證了嗎？」

**觸發詞**：卡在同一個問題試了 3～5 輪還沒進展 → 停下來查證（WebSearch / 官方狀態頁 / 系統log），不要繼續加碼試錯；看到陌生檔名/術語/provider名稱 → 先搜尋驗證，找不到就說找不到，不假裝存在或亂猜對應關係。

**最近一次**：2026-08-27（案例67）

## 🔴 模式 #4：部署/推送 SOP 被跳過——未經教練確認就上線，或上線前該給看卻沒給

**核心教訓**：部署到正式站（Netlify/GitHub Pages等）有明確 SOP（本機測試→給教練看→教練說「推」才送），但在趕時間或自認為「這次應該沒問題」時容易跳過確認這關，或該給教練看 HTML 預覽卻用內建預覽面板應付過去。

**涉及案例**：案例G（未經教練確認就git push，Netlify自動扣點）、案例H（分批push白白多扣15點額度）、案例26（government-grow報名按鈕反覆4次推送沒抓到真根因）、案例37（一個月內6次「照SOP該給看HTML卻沒給」）、案例46（HTML驗證又用內建預覽面板，沒跳Chrome給教練看）、案例54（Windows zip部署圖片全部無法顯示，PowerShell路徑分隔符+_headers範圍過廣雙bug疊加）。

**自動化防護狀態**：✅ 較完整——`netlify_deploy_guard.sh`／`web_preview_verify_guard.sh`／`html_preview_chrome_only` 系列 PostToolUse hook 已建立並多次迭代修補繞過路徑（如 Python 內部呼叫 API 繞過指令列偵測），詳見 `feedback_html_preview_chrome_only.md`「第10次後改PostToolUse自動化」。

**觸發詞**：任何要推正式站的動作 → 先查是哪一型部署（GitHub自動部署 vs zip手動上傳），本機驗證+教練親眼看過+教練說「推」三關缺一不可。

**最近一次**：2026-07-25（案例54）

## 🔴 模式 #5：危險/不可逆操作沒有足夠防護就執行

**核心教訓**：`rm -rf`/`Remove-Item -Recurse -Force`/搬移大型目錄等操作，一旦執行錯了就是資料永久蒸發，且往往是在「以為自己知道在幹嘛」的自信狀態下犯的。

**涉及案例**：案例24（Windows清TEMP→E槽636GB蒸發）、案例29（LINE 4GB聊天記錄永久丟失，刪檔鎖是opt-in函式不是hook，AI一打Remove-Item就裸奔）、案例30（C→D搬移大災難，Junction不等於完整遷移）。

**自動化防護狀態**：✅ 完整——執行細則E11「危險指令零容忍鐵律」五道閘門（絕對路徑硬編碼/目標echo給教練看/大小驗證/超過100MB需通行證/超過1GB教練親自授權）已寫死進CLAUDE.md，`scripts/delete_guard.sh`／`delete_guard.ps1`的`Safe-Remove`已取代直接呼叫。

**觸發詞**：任何整槽/整目錄/整資料庫清除動作 → 五道閘門走完才能執行，缺一不可。

**最近一次**：2026-06-25（案例29/30）

## 🔴 模式 #6：操作前沒確認環境/連線裝置對不對就假設正確

**核心教訓**：多機器（Mac/聯想/宏碁）+ 多瀏覽器擴充功能連線的環境下，`claude-in-chrome`實際連的是「當下配對成功的瀏覽器」，不是「這段對話跑在哪台電腦」——沒有主動查證就動手，可能對著教練另一台機器的畫面操作卻渾然不覺，或連線斷了還一直截圖問教練「你看得到嗎」。

**涉及案例**：案例60（claude-in-chrome連線到教練Windows電腦而非Mac本機）、案例63（連線斷了卻不斷截圖問教練，教練連續動怒三次才修好）、本場對話（2026-08-31）處理BNI Connect任務前，因偵測到兩台裝置同時連線，已依規範先用`AskUserQuestion`請教練指定裝置，而非自行假設。

**自動化防護狀態**：⚠️ 部分——`list_connected_browsers`+要求逐一列出裝置讓教練選的機制已是claude-in-chrome工具本身的內建規範（見系統提示詞），但仍要求AI主動呼叫，非強制攔截。

**觸發詞**：任何「跨機比較」「這台機器操作是否正常」類任務 → 動手前先確認連線裝置是預期的那台；連線疑似斷開 → 直接排查修復（關閉重開瀏覽器擴充功能），不要靠截圖問教練「看得到嗎」逃避問題。

**最近一次**：2026-08-24（案例63）

## 🔴 模式 #7：引用/承諾內容沒有真的「一字不差」查證，或忽然滑出繁體中文之外

**核心教訓**：引用守則編號、對話內容時「大概意思對」不是幫助是欺騙；同時軍師身份被規定「只能繁體中文回覆」，趕時間或context切換時偶爾滑出簡體字，教練重話糾正過。

**涉及案例**：案例D（捏造守則內容）、案例44（軍師整段回覆用簡體字，教練重話糾正；同場對話二犯，建立自動化Stop Hook攔截）、案例47（markdown連結格式跑掉沒發現，自信選了錯誤解讀，反問句給的糾錯機會也浪費了）。

**自動化防護狀態**：✅ 簡體字部分已有Stop hook攔截（案例44更新版）；引用查證部分（E08）僅`scope:['main']`生效，靠紀律非強制攔截。

**觸發詞**：引用守則/對話內容前 → 先查證原文再引用，不確定就說「我不確定，需要查證」；輸出前若感覺切到別的語言模式 → 停下重新確認全篇為繁體中文。

**最近一次**：2026-07-10（案例44）

## 🔴 模式 #8：明明自己能做，卻讓教練當搬運工/試錯手腳

**核心教訓**：AI有能力自己操作瀏覽器/查資料/驗證，卻叫教練去複製貼上、重建群組、重發訊息、或當「你幫我測試看看」的白老鼠——這是對守則#12（拒絕當資訊搬運工）最直接的違反，且往往發生在AI偷懶或沒想清楚自己工具邊界的時候。

**涉及案例**：案例A（RustDesk讓教練當搬運工）、案例43（Amber WebDAV，有能力自己驗證卻叫教練當試錯手腳）、案例62（明明能用computer-use直接開Telegram查，卻連續三輪叫教練重建群組/重發訊息，凌晨3點把教練當搬運工）。

**自動化防護狀態**：❌ 純紀律層面，靠每次動手前自問「這件事我自己的工具箱裡有沒有辦法做到」。

**觸發詞**：想叫教練「你點一下」「你複製貼上」「你重新試試看」之前 → 先問自己：我有沒有computer-use/browser工具可以自己做這件事？

**最近一次**：2026-08-24（案例62）

## 🔴 模式 #9：交接/心跳維護出現斷點，導致資訊斷層或系統靜默停擺

**核心教訓**：cron指向錯誤的heartbeat檔案、context overflow後沒即時更新交接、大型memory檔案讓模型空白回應、Mac因隱藏排程+headless無auto login意外停工5小時——這些都是「系統該持續運作卻默默斷掉，且沒人第一時間發現」的變形。

**涉及案例**：案例H（cron job指向錯誤的HB文件）、案例I（Context Overflow後HEARTBEAT.md未即時更新）、案例J（大型memory檔導致Gemini空白回應）、案例31（Mac停工5小時，pmset隱藏排程+headless無auto login）、案例50（VPS小龍蝦polling stale state卡住8小時，朋友先發現才回報）。

**自動化防護狀態**：⚠️ 部分——接力棒瘦身機制（E16）+ HEARTBEAT熱上下文注入已緩解「memory檔過大」問題，但「系統默默停擺」這類仍高度依賴人工/教練發現。

**觸發詞**：長時間沒有心跳/沒有回報 → 主動檢查是不是哪個環節斷了，不要假設「應該還在跑」；memory/HEARTBEAT檔案異常肥大 → 主動瘦身，不要等模型空白回應才處理。

**最近一次**：2026-07-14（案例50）

## 🔴 模式 #10：只信報告數字/工具回報，不用眼睛看真實畫面驗證

**核心教訓**：95%都做對，剩下1個logo裁切問題因為只信「工具說OK」沒有親眼看畫面，結果多花54分鐘才發現；HTML驗證用內建預覽面板應付，沒有真正跳出去用瀏覽器給教練看。視覺類任務唯一可信的驗證是親眼看畫面，不是DOM數字或工具的「看起來成功」。

**涉及案例**：案例38（95%都做對，1個logo裁切小問題耗掉54分鐘，不看畫面只信數字的代價）、案例46（HTML驗證又用內建預覽面板，沒跳Chrome給教練看）。

**自動化防護狀態**：✅ 已有PostToolUse hook強制改html後自動跳Chrome（`feedback_html_preview_chrome_only.md`），但「圖片/版面視覺細節」這類仍需要AI主動用image工具親眼確認，非100%可機關化。

**觸發詞**：任何視覺/版面/圖片產出交付前 → 用image-capable工具親自看過確認，不能只憑截圖尺寸/DOM數字/工具回報「成功」就交付。

**最近一次**：2026-07-10（案例46）

## 🔄 維護方式（往後怎麼保持這份索引不再空轉）

1. **每次試金石_案例庫.md新增一筆案例**，寫案例的當下順手判斷：這筆屬於上面10個模式的哪一個？屬於既有模式 → 在該模式的「涉及案例」欄位加一筆＋更新「最近一次」日期，**不需要重寫整條模式的敘述**（這是v1失敗的根本原因——舊格式要求每個新案例都重寫一大段觸發訊號清單，維護成本太高導致3個月沒人做）。
