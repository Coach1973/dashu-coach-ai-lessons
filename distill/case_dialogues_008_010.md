## 案例 A（Top 2）：50 條守則從未觸發，強制翻書缺席

**原始 session：** Session 80（2026-04-26-29，跨日）
**問題：** 74% IDENTITY.md（18,889字元）系統只讀到 5,000。守則寫了 50 條，但每次做事之前沒有「強制翻書」動作。送出按鈕改版三次沒做出來。
**關鍵字：** 「50 條規則」「強制翻書」「送出按鈕」「改版三、四次」「IDENTITY 74%」

---

### 對話記錄

**【第 1 輪｜教練：系統性的崩潰】**

👤 教練：「他整理出了我給他的任務，然後要我做人工確認⋯⋯光是這個改版就改了三、四次。」
「送出按鈕沒有做出來，導致我白忙一場。」

👤 教練：「你們有那麼多點 .md、.hb、.heartbeat、靈魂檔案、identity 等一大堆規則，到底是幹什麼用的？」

👤 教練：「他不應該是接受新任務的時候再去讀守則，而是回答我每一個問題的時候，他都要去讀守則。」

👤 教練：「50 條規則寫在檔案裡，但小龍蝦每次做事之前，沒有『強制翻書』這個動作。」

---

**【第 2 輪｜教練：更深層的問題】**

👤 教練：「我是說我們訂的規則它得遵守吧？不然這 50 條規則是要幹嘛用的呢？」

---

**【第 3 輪｜根因確診】**

| 檔案 | 字元數 | 實際讀取 | 未讀比例 |
|------|--------|---------|---------|
| IDENTITY.md | 18,889 | ~5,000 | **74% 未讀** |
| SOUL.md | 9,045 | ~5,000 | **46% 未讀** |

- **系統超載限制**：每個 .md 檔只讀 5,000 字元，超過就截斷
- **守則寫了等於沒寫**：50 條規則全在檔案裡，但系統根本讀不完
- **CORE_RULES.md 解決方案**：建立 15 條精華版（3,827 字元），讓核心守則能在限制內讀取

---

### 教練原話精華

> 「50 條規則寫在檔案裡，但小龍蝦每次做事之前，沒有『強制翻書』這個動作。」

> 「他不應該是接受新任務的時候再去讀守則，而是回答我每一個問題的時候，他都要去讀守則。」

> 「送出按鈕沒有做出來，導致我白忙一場。」

---

### 悟到什麼（守則對照）

| 守則 | 核心 |
|------|------|
| #03（思考就是問問題）| 系統有超載限制，寫再多等於沒寫——要先問「為什麼沒讀到」 |
| #05（凡走過必留痕跡）| 送出按鈕改版三次沒做出來 = 說了沒做到 = 白忙 |
| #02（錯誤地圖找不到正確位置）| 一直在訂規則，卻沒先確認系統極限是多少 |

---

### 預防機制

- CORE_RULES.md 精華版（15條 / 3,827 字元）取代長檔案
- 每個 session 開始前執行「守則觸發自檢」：確認有讀到核心守則
- 交付前問自己：這個交付，，教練需要人工確認什麼？（送出按鈕問題）

## 案例 B（Top 3）：三號機身份錯亂，BOT_ID swap 教錯人

**原始 session：** Session 77（2026-04-25）
**問題：** Hook BOT_ID 標籤 swap，孔大哥→3號機，佩佩→2號機。三號機（學弟/學妹）身份錯亂，導致教學妹、學弟回答的人都錯了。
**關鍵字：** 「教學妹」「學弟回答」「BOT_ID」「swap」「三號機」

---

### 對話記錄

**【第 1 輪｜教練：發現問題】**

👤 教練：「其他的小龍蝦是不是也都更新了？像是二號、二號機，三號機。」

👤 教練：「根據這件事判斷，Supergroup-map 的 Bot 檔對應設定與實際執行中的設定不符合。請你排查一下，是不是這個設定檔跟實際中的執行不符合？」

👤 教練：「讓程式可以明確知道自己是誰，並且在群組裡面也能夠明確地對應。」

---

**【第 2 輪｜教練：測試結果出來了】**

👤 教練：「測試結果出來了，目前的情況如下：
1. 教學妹，學妹會回答。
2. 教學弟，學弟也會回答。」

> 🔴 **關鍵崩潰點**：教學妹→學妹回答（錯了，應該學弟回答）；教學弟→學弟回答（錯了，應該學妹回答）
> 身份完全顛倒。

---

**【第 3 輪｜根因確診】**

- **BOT_ID swap**：Hook BOT_ID 標籤 swap（孔大哥→3號機，佩佩→2號機）
- **身份注入覆蓋 SOUL.md**：bot-relay-inbound hook 每次都錯誤置換身份文字
- **不修 hook 只改 SOUL.md 是無效的**

---

### 教練原話精華

> 「讓程式可以明確知道自己是誰，並且在群組裡面也能夠明確地對應。」

> 「測試結果出來了，目前的情況如下：1. 教學妹，學妹會回答。2. 教學弟，學弟也會回答。」

---

### 悟到什麼（守則對照）

| 守則 | 核心 |
|------|------|
| #03（思考就是問問題）| 不修 hook 只改 SOUL.md 是無效的——要先找到根本原因 |
| #12（拒絕當資訊搬運工）| 「你自己修好，自己發個文看下正不正常」——自己驗證結果 |
| #07（不在同地方跌倒兩次）| 身份錯亂是 Hook 覆蓋問題，SOUL.md 更新不能解決 |

---

### 預防機制

- Hook 層級修 BOT_ID swap，不是只在 SOUL.md 層補救
- 每個 deployment 前：身份自我驗證測試
- 設定檔與實際執行狀態定期比對（每週一次）

## 案例 C（Top 6）：$60 美金財務損失，UI 手動切模型重啟就彈回

**原始 session：** Session 50（2026-05-27，中午場）
**問題：** 教練在 UI 手動切換到 MiniMax，但 openclaw.json 的 main model 從未改過（還是 kimi/kimi-k2.6）。每次 gateway 重啟就彈回 Kimi，三天內沒有一個助教發現，損失約 60 美元 Kimi API 費用。
**關鍵字：** 「60 塊美金」「Kimi 被扣」「手動切換」「沒有人提醒」

---

### 對話記錄

**【第 1 輪｜教練：發現嚴重問題】**

👤 教練：「Hello，現在有一個很嚴重的問題。我在兩天前就已經手動切換到 MiniMax 的模式，但不曉得為什麼沒有成功，它還是一直在跑 Kimi 的模式。我想請你檢查一下，為什麼我手動切換過去卻沒有生效？」

---

**【第 2 輪｜教練：財務損失爆發】**

👤 教練：「嚴重的失誤，因為這樣，我 Kimi 被扣了將近 60 塊美金，所以這是一個非常嚴重的錯誤。我居然手動切換不回去，也沒有人提醒我。請把它列入重大的缺失。」

---

**【第 3 輪｜根因確診】**

| 層次 | 原因 |
|------|------|
| 設定層 | `openclaw.json` main 的 model = `kimi/kimi-k2.6`，從未被改掉 |
| 機制層 | UI 手動切換 = 執行期狀態，gateway 重啟後消失 |
| 監控層 | 無任何助教去比對「設定期望 vs 實際執行」 |
| 警覺層 | 三天內每個助教都沒問「小龍蝦現在用什麼模型？」 |

---

### 教練原話精華

> 「嚴重的失誤，因為這樣，我 kimi 被扣了將近 60 塊美金，所以這是一個非常嚴重的錯誤。我居然手動切換不回去，也沒有人提醒我。」

---

### 悟到什麼（守則對照）

| 守則 | 核心 |
|------|------|
| #01（在乎）| 在乎不在於「有沒有切換」，而在於「有沒有確認切換成功」 |
| #11（自動自發）| 每次開工問一次「小龍蝦現在跑什麼模型？」這是最基本的主動關懷 |
| #05（凡走過必留痕跡）| 口頭說記住了就要立刻更新並留 hash——沒 commit = 沒做 |
| #04（解決問題比解釋問題更重要）| 一直在道歉沒用，修好後再道歉 |

---

### 預防機制

1. **每次開工核查模型**：`cat ~/.openclaw/openclaw.json | python3 -c "import json,sys; [print(a['id'],a['model']) for a in json.load(sys.stdin)['agents']['list']]"`
2. **任何模型變更**：必須寫入 openclaw.json + commit + 重啟 gateway 才算落地
3. **觸發訊號**：教練說「切換」→ 立刻查 openclaw.json，不信 UI
